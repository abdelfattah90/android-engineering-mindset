Project 0

Kotlin Console Toolkit

A console expense tracker. It combines Kotlin fundamentals, Collections, OOP, error handling, unit tests, and Git.

Part 1Functional Requirements

  • Add an expense (amount, category, description, date) with input validation.
  • List expenses, edit an expense, and delete an expense.
  • Search and filter by category or period.
  • Sort by amount or date.
  • Report: total per category (groupBy) and the three largest expenses.
  • Extension: save expenses to a file (CSV or JSON) and load them at startup.

Part 2Acceptance Criteria

  • Invalid input shows a clear message and does not end the program.
  • Amounts are stored without floating-point errors (BigDecimal or integer minor units).
  • The code is split into model, logic, and console UI, with no business logic inside main.
  • Expected failures are represented with Result or a sealed class, not with exceptions used for control flow.
  • At least eight unit tests for the service logic, including edge cases.
  • A Git repository with a meaningful commit history (at least 10 commits) and a README with run instructions and an example.

Important Tips for Avoiding Ineffective Learning

Do not make memorizing topics the goal

You do not need to memorize every Kotlin function or Android API. You need to understand the concept, know when to use it, and be able to reach the right documentation.

Do not start with heavy Clean Architecture

Start with the UI and data layers, and add a domain layer and use cases when there is shared logic or complexity that justifies them. Do not turn every simple CRUD operation into dozens of files.

Do not put everything inside the ViewModel

A ViewModel suits screen state and coordination between the UI and the other layers. It should not become a home for all business logic or for direct handling of every data source.

Do not use GlobalScope as a default

Tie a coroutine to the right scope and lifecycle, and respect structured concurrency and cancellation.

Do not block the main thread

Any I/O or expensive computation must run off the main thread through a suitable design, with results returned to the UI through state and flow mechanisms.

Do not treat every background task the same

  • A coroutine for work tied to the life of a process, a screen, or a specific scope.
  • WorkManager for deferrable, persistent work that must stay scheduled across app closes and device restarts, within system limits.
  • A foreground service for work visible to the user that needs to run continuously in cases the policies support.

Do not put secrets inside a mobile app

Any value embedded in an APK can be extracted to varying degrees. Do not store private backend secrets in the app. Use a backend to control sensitive operations, and protect tokens and data according to your threat requirements.

Do not use certificate pinning without a reason

Poor implementation can break connectivity when certificates rotate or the infrastructure changes. Use it only after studying the threat model and setting up a reliable plan for updates and exceptions.

Do not treat offline-first as just a cache

Offline-first requires choosing a source of truth, a write and sync policy, and handling conflicts, failures, and retries.

Do not overuse multi-module

Start with a simple structure. Add modules when they help isolate responsibilities, speed up builds, enable multiple teams, or provide real reuse.

Learn testing from the beginning

Do not postpone tests to the end of the curriculum. Test functions, repositories, ViewModels, and UIs as you learn each new way of managing behavior.

Do not optimize performance by guessing

Measure first, find the bottleneck, change one thing, and measure again. Use profilers and benchmarks where they fit.

Watch compatibility and versions

Always check that the JDK, Gradle, Android Gradle Plugin, Kotlin, Compose compiler plugin, and SDK libraries are compatible. Use the official release documentation, and do not copy version numbers from this plan as if they were fixed.

Review Google Play policies before launch

Target API level requirements and the policies on privacy, permissions, and SDKs change. Check the actual policy at release time, not an old article or a remembered fact.

Build a real portfolio

It is better to have 3–5 complete, documented, runnable projects than dozens of copied ones. Give each project a clear problem, engineering decisions, tests, and run instructions.

Summary

Completing this plan does not mean knowing every library or API in Android. It means having a strong foundation that lets you:

  • Write clean Kotlin and understand object-oriented and functional programming and data structures.
  • Use Git and work in a way that suits a development team.
  • Understand the Android platform, the app lifecycle, and system components.
  • Build modern UIs with Jetpack Compose, while understanding the View system for existing projects.
  • Design apps with clear layers and unidirectional data flow, without unjustified architectural complexity.
  • Handle local storage, networking, sync, and offline work.
  • Integrate device capabilities, Google services, and Firebase as needed.
  • Test the app, analyze code, debug, and measure performance.
  • Protect data, connections, and credentials, and prepare the app for release.
  • Build a production-ready app, then monitor and maintain it after launch.

The real measure of success: you can take an app idea, turn it into a technical design, then build, test, secure, publish, and maintain it, and justify your technical decisions instead of just applying ready-made recipes.
