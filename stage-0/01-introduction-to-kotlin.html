What Kotlin Is - ما هي Kotlin

قبل الدخول في Android نحتاج أن نفهم الأداة التي سنكتب بها. بدأت JetBrains، الشركة التي تصنع IntelliJ IDEA (الذي بُني عليه Android Studio)، العمل على Kotlin عام 2010 وكشفت عنها عام 2011. كانت تبني منتجاتها بـ Java على JVM وأرادت لغة أفضل منها، لكن بشرط واضح: ألا تفرض إعادة كتابة ما كُتب بـ Java.

تعريف

Kotlin لغة statically typed عامة الأغراض تجمع الأسلوب الكائني (object-oriented) والوظيفي (functional)، طوّرتها JetBrains وهي مفتوحة المصدر برخصة Apache 2.0. وصفتها JetBrains عند الإصدار 1.0 بأنها pragmatic: صُمّمت حول حالات استعمال حقيقية، وتركّز على interoperability وsafety وclarity وtooling.

يمكن تلخيص المشكلات التي استهدفتها في أربع:

  • الكود المتكرر (boilerplate): صنف يحمل بيانات في Java يحتاج حقولًا وconstructor وgetters وequals وhashCode وtoString، فيضيع المنطق الفعلي بين السطور. تعالجه الصياغة المختصرة.
  • أخطاء القيم الفارغة: أي مرجع في Java قد يكون null والمترجم لا يحذّرك، فتظهر NullPointerException وقت التشغيل بعيدًا عن سببها. يعالجها نظام الأنواع بفصل ما يقبل null عمّا لا يقبله.
  • كلفة الترحيل: لا تستطيع شركة إعادة كتابة ملايين الأسطر لتجرّب لغة جديدة، ولذلك صُمّمت Kotlin لتعيش مع Java في المشروع نفسه.
  • دعم الأدوات: لغة بلا IDE جيد لا تُستعمل، ولذلك طوّرت JetBrains اللغة وأدواتها معًا.

قد تسأل: لماذا لم تُصلَح Java نفسها؟ Java تطورت فعلًا (أضافت var وrecords مثلًا)، لكن لغة بهذا العمر لا تستطيع أن تجعل كل String غير فارغة دون كسر كود قائم. لغة جديدة تبدأ بنظام أنواع يفصل بين الحالتين من اليوم الأول. هذا تفسير هندسي لسبب وجود Kotlin وليس حكمًا بأن Java لغة سيئة، وسنقارن بينهما بإنصاف في الموضوع الرابع.

ملاحظة

Kotlin-first لا تعني أن Java ممنوعة. تعني، بحسب Google، أن التوثيق والعيّنات والمكتبات والأدوات الجديدة تُصمَّم لـ Kotlin أولًا مع استمرار دعم Java. أما Jetpack Compose، أداة بناء الواجهات الحديثة في Android، فمكتوبة بـ Kotlin وتُستعمل بها فقط. لهذا تبدأ هذه السلسلة بـ Kotlin.

كيف تعمل Kotlin داخليًا؟ على JVM لا توجد «آلة Kotlin». المترجم kotlinc يقرأ ملفات .kt وينتج ملفات .class بصيغة JVM bytecode نفسها التي ينتجها مترجم Java. الـ JVM لا يعرف بأي لغة كُتب الـ bytecode الذي يشغّله، وهذا أساس التوافق مع Java الذي نعود إليه في الموضوعين الثاني والرابع.

لنتحقق من ذلك. الملف التالي فيه دالة واحدة مكتوبة خارج أي class. ماذا تتوقع أن تجد في مجلد out بعد ترجمته، وما الدوال الموجودة داخل الـ class الناتج؟

Hello.kt — دالة واحدة بلا class Kotlin 
fun main() {
    println("Hello, Musab")
}
Terminal — ترجمة الملف وفحص الناتج Bash 
kotlinc Hello.kt -d out
ls out
javap -p -cp out HelloKt
النتيجة
Terminal 
HelloKt.class
META-INF
Compiled from "Hello.kt"
public final class HelloKt {
  public static final void main();
  public static void main(java.lang.String[]);
}

التوقع الشائع هو ملف Hello.class فيه دالة main واحدة. الواقع مختلف في ثلاثة أمور. أولًا، الدوال المكتوبة خارج أي class تُجمَّع في class يحمل اسم الملف مع اللاحقة Kt، ولهذا ظهر HelloKt.class. ثانيًا، ظهرت دالتا main: الأولى هي دالتنا بلا parameters، والثانية main(String[]) ولّدها المترجم لتستدعي الأولى، لأن JVM تبحث عن نقطة دخول بهذا الشكل تحديدًا. ثالثًا، المجلد META-INF يحمل metadata خاصة بـ Kotlin يقرؤها المترجم حين يُستعمل هذا الناتج من كود Kotlin آخر.

الأداة javap تأتي مع JDK وتعرض محتوى ملف .class، وهي تعمل هنا لأن الناتج bytecode عادي. تترتب على ذلك نتائج عملية: تستطيع Java أن تستدعي هذا الكود كأي class آخر، وتعمل أدوات JVM (debuggers وprofilers) على الناتج، ويعامل Android هذا الـ bytecode كما يعامل ناتج Java، كما سنرى في الموضوع الثالث.

ملاحظة

تسمية HelloKt للدوال ذات المستوى الأعلى سلوك موثّق لأن Java تعتمد عليه عند الاستدعاء. أما تفاصيل التعليمات داخل الـ bytecode فهي تنفيذ داخلي للمترجم وقد تتغير بين الإصدارات، فلا تبنِ عليها.

انتبه

الخطأ: التعامل مع Kotlin كأنها بيئة تشغيل منفصلة عن Java، أو افتراض أن نظام أنواعها القوي يلغي أخطاء التشغيل. نتيجته: عند ظهور NullPointerException أو NoClassDefFoundError في برنامج Kotlin تبحث في المكان الخطأ. الإصلاح: اعتبر Kotlin مترجمًا فوق JVM. ضماناتها تُفحص وقت الترجمة لما يراه المترجم فقط، وتحمل رسائل الأخطاء أسماء الـ classes المولّدة (مثل HelloKt) مع اسم ملف .kt ورقم السطر، فتدلّك على كودك مباشرة.

Core Language Traits - الخصائص الأساسية للغة

رأينا أن Kotlin مترجم فوق JVM ينتج bytecode عاديًا. نتناول الآن أربع خصائص تعطي اللغة طابعها، ونشرح لكل منها المشكلة التي تحلّها وكيف تعمل وأين تضعف: الصياغة المختصرة، والأمان من القيم الفارغة، والتشغيل البيني مع Java، واستنتاج الأنواع.

Concise Syntax - الصياغة المختصرة

المشكلة: الكود الذي يكرّر ما يعرفه المترجم أصلًا يُبطئ القراءة، لأن القارئ يبحث عن سطر المنطق بين سطور الشكل. تعالج Kotlin ذلك بأن يولّد المترجم ما يمكن اشتقاقه. المثال الأوضح هو data class: تعلن الخصائص في الـ primary constructor، فيولّد المترجم equals وhashCode وtoString وcopy. لا سحر هنا: الدوال المولّدة موجودة فعلًا في الـ bytecode الناتج، والاختصار في المصدر فقط.

في متجر Musab الصغير منتجان لهما الاسم والسعر نفسهما. Ahmed قادم من Java ويعرف أن == على الكائنات يقارن المراجع. ماذا تتوقع أن تطبع الأسطر الأربعة التالية؟

Product.kt — data class ومقارنة كائنين Kotlin 
data class Product(val name: String, val priceCents: Int)

fun main() {
    val keyboard = Product("Keyboard", 4999)
    val same = Product("Keyboard", 4999)
    println(keyboard == same)
    println(keyboard === same)
    println(keyboard)
    println(keyboard.copy(priceCents = 3999))
}
النتيجة
Console 
true
false
Product(name=Keyboard, priceCents=4999)
Product(name=Keyboard, priceCents=3999)

إن توقّعت false في السطر الأول بحكم عادة Java فالفرق في معنى العامل. == في Kotlin يستدعي equals فيقارن المحتوى، فكان الناتج true. أما === فيقارن الهوية (هل هما الكائن نفسه)، وهو ما يفعله == في Java على الكائنات، فكان الناتج false لأن هناك كائنين منفصلين. السطر الثالث يظهر فيه toString المولّدة، والرابع نسخة جديدة غُيّرت فيها الخاصية المسماة فقط، والكائن الأصلي لا يتأثر لأن خصائصه val.

الاختصار لا يقف عند الأصناف. الدالة التالية تجمع أربعة اختصارات: جسم الدالة تعبير واحد بعد =، وقيمة افتراضية لـ parameter، وتضمين المتغيرات والتعابير داخل النص بالعلامة $، وتسمية الـ arguments عند الاستدعاء بأي ترتيب.

Syntax.kt — expression body وdefault وnamed arguments Kotlin 
fun priceLabel(name: String, priceCents: Int, unit: String = "cents"): String =
    "${name.uppercase()}: $priceCents $unit"

fun main() {
    println(priceLabel("Keyboard", 4999))
    println(priceLabel(priceCents = 2500, name = "Mouse"))
}
Console 
KEYBOARD: 4999 cents
MOUSE: 2500 cents

لاحظ أيضًا val في الأمثلة: تعلن مرجعًا لا يُعاد إسناده، بينما var يسمح بإعادة الإسناد. القاعدة المتّبعة هي البدء بـ val وعدم استعمال var إلا عند الحاجة.

البدائل موجودة: أضافت Java الـ records (من Java 16) فصار الصنف الحامل للبيانات قصيرًا فيها أيضًا، وتولّد مكتبات مثل Lombok الكود نفسه عبر annotation processing. لذلك لا تكمن ميزة Kotlin في الصنف الحامل للبيانات وحده، بل في أن الاختصار جزء من اللغة ويشمل الدوال والـ arguments كذلك، دون أداة إضافية. سنضع كود Java الكامل بجانب سطر Kotlin الواحد في الموضوع الرابع.

انتبه

الخطأ: افتراض أن equals المولّدة تقارن كل خصائص الصنف. هي تقارن فقط الخصائص المعلنة في الـ primary constructor. نتيجته: كائنان يختلفان في خاصية معلنة داخل جسم الصنف (مثل note في سلة Ahmed) يُعدّان متساويين فعلًا. الإصلاح: انقل الخاصية إلى الـ constructor إن كان يجب أن تدخل في المساواة، وإلا فاكتب equals وhashCode بنفسك.

Null Safety - الأمان من القيم الفارغة

المشكلة: في Java أي مرجع قد يكون null والمترجم لا يعترض على استعماله، فتظهر NullPointerException وقت التشغيل، وغالبًا بعيدًا عن المكان الذي دخلت منه القيمة الفارغة. ترى Kotlin أن هذا الفحص مكانه المترجم لا المستخدم.

تعريف

Null safety في Kotlin أن تكون قابلية القيمة للفراغ جزءًا من نوعها: String لا تقبل null أبدًا، وString? تقبله، ولا يُسمح باستعمال النوع القابل للفراغ قبل معالجة الحالة الفارغة.

كيف تعمل داخليًا؟ الفحص يقوم به المترجم. في الـ bytecode يظهر النوعان String وString? بالنوع java.lang.String نفسه، ويُحفظ الفرق في metadata وفي annotations يضيفها المترجم لتراها أدوات Java. وعند حدود الكود العام يُدخل المترجم في بداية الدوال العامة فحصًا لكل parameter غير قابل للفراغ، فإذا استدعاها كود Java بـ null فشل الاستدعاء فورًا برسالة تسمّي الـ parameter بدل أن تنتشر القيمة الفارغة داخل البرنامج. سنرى أثر هذا الفحص عمليًا في الموضوع الرابع.

ملاحظة

ما تضمنه اللغة هو أن النوعين مختلفان عند المترجم. أما شكل الفحص المُدخَل ومكانه في الـ bytecode فهو تفصيل تنفيذ قد يتغير بين الإصدارات.

البديل في Java هو Optional وannotations مثل @Nullable. الأول نوع مكتبة يغلّف القيمة في كائن إضافي، والمرجع Optional نفسه قد يكون null، ولا تفرض اللغة استعماله. الثانية تنتج تحذيرات من الأدوات لا أخطاء من اللغة. اختارت Kotlin فرض القاعدة في نظام الأنواع، دون كائن إضافي وقت التشغيل. لنرَ ما يحدث حين نخالفها:

Checkout.kt — خطأ مقصود: لا يُترجم Kotlin 
fun cityNameLength(city: String?): Int {
    return city.length
}
Compiler 
Checkout.kt:2:16: error: only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type 'String?'.
    return city.length
               ^

رفض المترجم السطر قبل أن يصل البرنامج إلى المستخدم، وهذا المقصود: انتقل الخطأ من وقت التشغيل إلى وقت الترجمة. تعطيك Kotlin أربع طرق لمعالجة الحالة الفارغة. في Java، استدعاء length() على مرجع فارغ يرمي استثناء. ماذا تتوقع أن يفعل السطر الأول في البرنامج التالي حين تكون city فارغة: يرمي استثناء، أم يطبع null، أم يطبع 0؟ وماذا عن بقية الأسطر؟

NullSafety.kt — safe call وElvis وsmart cast و!! Kotlin 
fun main() {
    val city: String? = null
    val country: String? = "Egypt"

    println(city?.length)
    println(city?.length ?: 0)

    if (country != null) {
        println(country.length)
    }

    try {
        println(city!!.length)
    } catch (e: Exception) {
        println(e::class.simpleName)
    }
}
النتيجة
Console 
null
0
5
NullPointerException

السطر الأول طبع null ولم يرمِ استثناء: العامل ?. (safe call) يتوقف ويُرجع null حين يكون المستقبِل فارغًا، ولذلك نوع التعبير كله Int? وليس Int. السطر الثاني استعمل ?: (Elvis) لتحديد قيمة بديلة فصار النوع Int والناتج 0. في الثالث عرف المترجم، بعد الفحص country != null، أن country غير فارغة داخل الـ if فسمح باستعمال length مباشرة، وهذا هو smart cast. أما الرابع فقال فيه !! للمترجم «أنا متأكد»، وتحمّلنا المسؤولية، فرُميت NullPointerException والتقطناها وطبعنا اسمها.

الضمانة تسري على ما يراه المترجم فقط، وتضعف في مواضع محددة. أولها !! لأن المبرمج يتجاوز بها الفحص بإرادته. وثانيها حدود Java التي لا يعرف المترجم عندها قابلية الفراغ، وهو موضوع الخاصية التالية. وثالثها المكتبات التي تملأ الحقول بالـ reflection دون المرور عبر الـ constructor، فقد تضع null في خاصية معلنة غير قابلة للفراغ. ورابعها lateinit التي تؤجل التهيئة، فتُرمى UninitializedPropertyAccessException إن قُرئت قبل أن تُهيّأ.

انتبه

الخطأ: استعمال !! لإسكات المترجم كلما اعترض. نتيجته: تعود NullPointerException كما رأينا في السطر الرابع، وتفقد الفائدة التي جئت من أجلها. الإصلاح: عالج الحالة الفارغة بـ ?. أو ?: أو فحص صريح، واسأل أولًا لماذا وصلت القيمة قابلة للفراغ إلى هذا الموضع، فقد يكون الحل تغيير النوع عند المصدر.
