Introduction to Kotlin

Kotlin ليست مجرد Java بصياغة أقصر؛ إنها لغة صُممت لتقليل الأخطاء الشائعة، وتحسين وضوح الكود، وتسهيل تطوير الأنظمة الكبيرة دون التخلي عن النظام البيئي لـ Java. لفهم مكانتها في Android، سنبدأ بالمشكلات الهندسية التي دفعت إلى تصميمها، ثم نفكك خصائصها الأساسية: concise syntax وnull safety وJava interoperability وtype inference. بعد ذلك سنحدد أين تُنفَّذ Kotlin وكيف تختلف بيئة Android عن JVM، ثم نقارنها بـ Java على مستوى اللغة والتكامل وruntime. وأخيرًا سنفهم دورة إصدارات Kotlin ودور K2 compiler، لأن اختيار إصدار اللغة جزء من توافق منظومة البناء، وليس مجرد تغيير رقم في المشروع.

1. What Kotlin is and the problems it was designed to solve

1.1 المشكلة

قبل Kotlin، كان تطوير تطبيقات Android يعتمد بدرجة كبيرة على Java، وهي لغة statically typed وذات نظام بيئي واسع، لكنها تفرض على المطور كتابة قدر من الكود المتكرر، ولا تعبّر عن احتمالية null في نظام الأنواع بالطريقة التي يفعلها Kotlin.

المشكلة لم تكن أن Java عاجزة عن بناء تطبيقات موثوقة؛ بل أن بعض المخاطر والتكاليف كانت تُترك بدرجة أكبر لانضباط المطور والاختبارات.

لنفترض وجود تطبيق مصرفي يعرض بيانات حساب العميل. قد تصل البيانات من API دون قيمة للاسم المعروض، أو قد تُرجع مكتبة قديمة null رغم أن المستهلك يتوقع كائنًا صالحًا.

في Java التقليدية:

String customerName = account.getCustomer().getName();

قد يتسبب أي عنصر وسيط يساوي null في NullPointerException وقت التشغيل.

كذلك، عند بناء نماذج البيانات، وتوصيل callbacks، وتعريف constructors وgetters وsetters، قد يتكرر عدد كبير من الأسطر التي لا تضيف منطقًا تجاريًا جديدًا.

كان المطلوب لغة تحقق عدة أهداف في الوقت نفسه:

  • تقليل boilerplate دون التضحية بالـ static typing.
  • جعل حالات الخطأ الشائعة، وخصوصًا التعامل مع null، أوضح أثناء كتابة الكود ووقت compile.
  • المحافظة على القدرة على استخدام مكتبات Java الحالية.
  • تقديم لغة مناسبة لتطبيقات كبيرة يمكن تطويرها وصيانتها تدريجيًا.
  • توفير أسلوب برمجي أكثر تعبيرًا، مع دعم object-oriented وfunctional programming.

بدأ تطوير Kotlin في JetBrains عام 2010، وأُعلن عنها مفتوحة المصدر عام 2012، ثم وصلت إلى الإصدار المستقر 1.0 في فبراير 2016. لم يكن الهدف إنشاء منصة تشغيل جديدة تنافس JVM، بل إنشاء لغة حديثة تستطيع الاستفادة من المنصات الموجودة والتكامل معها. Kotlin FAQ

1.2 كيف يعمل

النموذج الذهني

تعامل مع Kotlin باعتبارها لغة برمجة مستقلة ذات type system وcompiler خاصين بها، ويمكنها استهداف أكثر من منصة.

أي أن Kotlin تحدد كيف تكتب الكود وكيف تُفحص صحته، بينما تحدد المنصة المستهدفة كيف يُترجم الكود وكيف يُنفَّذ.

هذا نموذج توضيحي للمسارات العامة؛ فطريقة البناء والتفاصيل الوسيطة تختلف حسب الـ target والـ build tools.

في Android تحديدًا، تستفيد Kotlin من توافقها مع Java وJVM bytecode. لا تحتاج إلى استبدال Android Runtime أو إنشاء runtime مستقل للتطبيق.

من المهم فهم الفرق بين لغة البرمجة وبيئة التنفيذ:

  • Kotlin هي اللغة التي تكتب بها.
  • Kotlin Compiler هو المسؤول عن تحويل الكود والتحقق من صحته.
  • Android SDK يوفّر APIs التي تتعامل مع نظام Android.
  • Android Runtime (ART) هو بيئة تشغيل كود التطبيقات على أجهزة Android الحديثة.

إذًا، Kotlin لا تمنح تطبيق Android صلاحيات إضافية، ولا تغيّر قواعد نظام التشغيل المتعلقة بالذاكرة أو العمليات أو threads لمجرد أنك استخدمتها بدل Java.

1.3 مثال واقعي

لنفترض أن تطبيق توصيل يحتاج إلى بناء نموذج يمثل حالة الطلب:

data class DeliveryStatus(
    val orderId: String,
    val driverName: String?,
    val estimatedMinutes: Int,
    val isDelivered: Boolean
)

data class هي فئة مخصصة أساسًا لحمل البيانات، ويولّد لها Kotlin تلقائيًا وظائف شائعة مثل equals() وhashCode() وtoString() وcopy().

وجود String? يعبّر مباشرة عن أن اسم السائق قد يكون غير متاح، بينما orderId: String يعبّر عن أن المعرّف يجب أن يكون غير فارغ وفق عقد Kotlin.

هذا التصميم لا يلغي الحاجة إلى validation؛ فقد يكون الاسم فارغًا كنص ""، وقد تكون قيمة estimatedMinutes سالبة نتيجة خطأ في البيانات. لكنه يجعل بعض شروط العقد جزءًا من type system بدل أن تبقى مجرد اتفاق غير موثق بين المطورين.

1.5 أين يفشل

الخطأ الأول: الاعتقاد بأن Kotlin تمنع جميع أخطاء runtime.

قد يمنع type system أنواعًا كثيرة من الأخطاء، لكنه لا يضمن صحة منطق التطبيق أو البيانات القادمة من الشبكة أو سلامة التعامل مع الذاكرة والعمليات المتزامنة.

الأعراض قد تكون crash رغم أن جميع أنواع Kotlin تبدو صحيحة. عند التشخيص، افحص stack trace والـ input الفعلي وشروط العمل، ولا تفترض أن استخدام Kotlin يعني استحالة حدوث أخطاء.

الخطأ الثاني: الاعتقاد بأن Kotlin تستبدل Android SDK أو ART.

Kotlin لا توفر نسخة بديلة من Activity أو Context أو Android lifecycle. إنها تتيح كتابة الكود الذي يتعامل مع هذه المكونات.

الخطأ الثالث: اعتبار تقليل عدد الأسطر دليلًا كافيًا على جودة التصميم.

يمكن كتابة كود Kotlin قصير جدًا لكنه غامض أو هش، خصوصًا مع الاستخدام المفرط للـ extension functions والـ lambdas والـ implicit type inference.

عند مراجعة الكود، اسأل: هل يستطيع مهندس آخر فهم العقد والآثار الجانبية من دون تتبع عدد كبير من التعبيرات المختصرة؟

1.6 قاعدة القرار

استخدم Kotlin كلغة أساسية لمشروع Android جديد لأنها اللغة الموصى بها رسميًا وتوفر تكاملًا كاملًا مع Android APIs وJava libraries.

أما في مشروع Java قائم، فأدخل Kotlin تدريجيًا عندما تحقق فائدة واضحة، دون افتراض ضرورة إعادة كتابة النظام.

2. Core language traits

تقوم قوة Kotlin على مجموعة خصائص مترابطة، وليس على syntax مختصر فقط. فهم هذه الخصائص مهم لأنك ستستخدمها لاحقًا في تصميم Android Architecture Components وJetpack Compose، حيث تعتمد المكتبات الحديثة على type system وlambdas وخصوصًا nullability بشكل كبير.

2.1 Concise Syntax

المشكلة

في التطبيقات الكبيرة، يتكرر عدد كبير من الأسطر لأداء مهام متشابهة: إنشاء objects، وتعريف properties، وتوصيل parameters، وكتابة getters وsetters، والتعامل مع collections.

هذا التكرار له كلفة تتجاوز عدد الأسطر؛ فهو يزيد مساحة الكود التي تحتاج إلى مراجعة وتعديل واختبار.

لكن اختصار الكود وحده ليس هدفًا كافيًا. الاختصار الذي يخفي السلوك أو يجعل الكود أصعب في القراءة ليس تحسينًا هندسيًا.

كيف يعمل

النموذج الذهني

Kotlin تجعل عددًا من الأنماط الشائعة تعبيرات مباشرة في اللغة، ثم يتولى compiler توليد التفاصيل اللازمة.

أهم مثال على ذلك هو data class، لكن توجد آليات أخرى مثل primary constructor وproperties وdefault parameters وexpression body.

1. Primary Constructor

هو constructor يُعرَّف مباشرة بعد اسم الـ class، ويمكن من خلاله تعريف properties وتهيئتها.

class BankAccount(
    val accountId: String,
    var availableBalance: Long
)

بدلًا من كتابة constructor منفصل وتعريف المتغيرات وإسناد القيم إليها، يجمع Kotlin هذه العمليات في declaration واحدة.

val تعني أن المرجع لا يمكن إعادة إسناد قيمة جديدة إليه بعد تهيئته، بينما var تسمح بإعادة الإسناد.

لاحظ أن val لا تعني بالضرورة أن الكائن immutable؛ فإذا كانت القيمة تشير إلى MutableList، يمكن تعديل محتويات القائمة رغم عدم إمكانية إعادة إسناد المرجع.

2. Properties

الـ property هي عضو يمثل قيمة داخل class، ويوفر Kotlin آلية getter وsetter لها دون الحاجة إلى كتابة دوال الوصول يدويًا في الحالات العادية.

class Cart {
    var itemCount: Int = 0
        private set

    fun addItem() {
        itemCount++
    }
}

هنا يستطيع الكود الخارجي قراءة itemCount، لكنه لا يستطيع تعديلها مباشرة لأن setter أصبح private.

3. Expression Body

تسمح Kotlin بكتابة دالة يكون جسمها تعبيرًا واحدًا، وتُستنتج قيمة الإرجاع من التعبير.

fun calculateTotal(
    subtotal: Long,
    deliveryFee: Long = 0
) = subtotal + deliveryFee

default parameter هي قيمة افتراضية لمعلمة الدالة، تُستخدم عندما لا يمرر المستدعي قيمة لها.

يمكن استدعاء الدالة هكذا:

val total = calculateTotal(subtotal = 12500)

فيكون total مساويًا لـ 12500 دون الحاجة إلى تمرير deliveryFee.

هذه الميزة تقلل الحاجة إلى تعريف overloads متعددة للدالة نفسها.

4. Data Classes

تساعد على تعريف نماذج البيانات دون كتابة وظائف المقارنة والنسخ والعرض يدويًا.

data class Money(
    val amountMinor: Long,
    val currency: String
)

يمكن الاستفادة من الوظائف المولدة:

val original = Money(15000, "EGP")

val updated = original.copy(amountMinor = 18000)

الـ copy() هنا تنشئ object جديدًا باستخدام قيم الكائن الأصلي، مع استبدال القيم التي حددتها.

لكنها لا تنشئ deep copy تلقائيًا؛ فإذا احتوت إحدى properties على قائمة mutable، فقد يشترك الكائنان في مرجع القائمة نفسها.

هذه نقطة مهمة في تطبيقات Android التي تعتمد على immutable state لتقليل المشكلات الناتجة عن مشاركة البيانات القابلة للتعديل.

مثال واقعي

في تطبيق تجارة إلكترونية، لديك بيانات المنتج:

data class Product(
    val id: String,
    val name: String,
    val priceMinor: Long,
    val discountMinor: Long = 0
)

يمكنك تمثيل المنتج وتحديث بعض بياناته دون كتابة constructors وgetters وcopy methods يدويًا.

الأهم أن تعريف البيانات أصبح واضحًا في موضع واحد، ويمكن لأي مهندس قراءة الـ class ومعرفة القيم التي يحتاج إليها المنتج.

لاحظ استخدام priceMinor بدلًا من price؛ تمثيل المبالغ المالية بوحدات العملة الصغرى كأعداد صحيحة يتجنب بعض مشكلات الدقة التي تظهر مع floating-point arithmetic.

البدائل

يمكنك كتابة classes تقليدية عندما تحتاج إلى تحكم خاص في الإنشاء أو السلوك، أو استخدام data class لنماذج البيانات، أو استخدام Java records عند العمل مع Java حديثة.

اختر data class عندما تكون الهوية الأساسية للكائن مرتبطة بقيم بياناته، وليس عندما يمثل الكائن كيانًا له هوية وسلوك معقدان ويجب أن يتحكم في دورة حياته وتعديلاته.

أين يفشل

الخلط بين val وimmutability.

val products = mutableListOf("Laptop")

products.add("Phone")

هذا الكود صحيح لأن المرجع products لم يتغير، لكن محتويات القائمة تغيرت.

الإفراط في الاختصار.

الدالة التالية صحيحة من ناحية اللغة:

fun processOrder(order: Order) =
    if (order.isPaid) order.items.sumOf { it.price } else 0

لكن عندما يصبح المنطق التجاري معقدًا، قد يكون جسم الدالة متعدد الأسطر أوضح، ويسهّل إضافة validation والتعامل مع الأخطاء.

الاعتماد على copy() بوصفها Deep Copy.

قد يؤدي ذلك إلى مشاركة mutable objects بين نسختين من نموذج البيانات، فتظهر تغييرات غير متوقعة في أكثر من مكان.

قاعدة القرار

استخدم concise syntax لتقليل الكود المتكرر، لا لإخفاء المنطق.

استخدم data class لتمثيل البيانات، وval افتراضيًا عندما لا تحتاج إلى إعادة إسناد المرجع، واحتفظ بالكود متعدد الأسطر عندما يجعل شروط العمل والآثار الجانبية أوضح.

2.2 Null Safety

المشكلة

null تمثل غياب القيمة، لكنها قد تتحول إلى مشكلة عندما يتعامل الكود معها كما لو كانت object موجودة.

في Android، يمكن أن تظهر هذه الحالة في أماكن كثيرة:

  • استجابة API لا تحتوي على بيانات اختيارية.
  • سجل قديم في قاعدة بيانات لا يحتوي على حقل معين.
  • Java API ترجع null.
  • بيانات المستخدم لم تُحمَّل بعد.
  • قيمة تعتمد على نتيجة عملية غير متزامنة.

إذا لم يكن غياب القيمة ظاهرًا في عقد الدالة، فقد يكتب المستهلك كودًا يفترض وجود object ثم يفشل عند التشغيل.

كيف يعمل

النموذج الذهني

تعامل Kotlin مع nullable وnon-nullable بوصفهما نوعين مختلفين.

val customerName: String = "Ahmed"
val secondaryPhone: String? = null

String لا تسمح بإسناد null إليها من كود Kotlin العادي، بينما String? تسمح بذلك.

الرمز ? جزء من نظام الأنواع نفسه، وليس مجرد تعليق توثيقي.

هذا يجعل compiler قادرًا على التحقق من طريقة التعامل مع القيمة قبل تشغيل البرنامج.

الآلية الداخلية

عندما يقرأ compiler تعبيرًا من نوع String?، لا يسمح باستدعاء العمليات الخاصة بـ String مباشرة دون التأكد من عدم وجود null.

مثلًا:

val phone: String? = getCustomerPhone()

println(phone.length)

هذا الكود لا يُقبل؛ لأن phone قد تكون null.

أمامك عدة طرق للتعامل مع الاحتمال.

1. Safe-call operator ?.

هو operator يسمح باستدعاء property أو function فقط عندما يكون المرجع غير فارغ.

val length = phone?.length

إذا كانت phone تساوي null، تصبح النتيجة null أيضًا.

لاحظ أن نوع length سيكون Int?، لأن العملية نفسها يمكن أن تنتج قيمة غير موجودة.

2. Elvis operator ?:

هو operator يوفر قيمة بديلة عندما يكون التعبير الموجود على يساره null.

val length = phone?.length ?: 0

النتيجة هنا دائمًا Int، وليس Int?.

يمكن استخدام return أو throw على يمين Elvis أيضًا:

fun getPhoneLength(phone: String?): Int {
    val value = phone ?: return 0

    return value.length
}

3. Smart Cast

هو قدرة compiler على استنتاج أن قيمة معينة أصبحت من نوع أكثر تحديدًا بعد فحص شرط منطقي.

fun displayPhone(phone: String?) {
    if (phone != null) {
        println(phone.length)
    }
}

داخل الشرط، يعرف compiler أن phone غير فارغة، ولذلك يسمح باستدعاء length دون استخدام ?..

لا يحدث هذا في كل الحالات؛ يجب أن تكون القيمة مستقرة بما يكفي حتى يضمن compiler أن الفحص ما زال صالحًا عند استخدامها. لذلك قد يفشل smart cast مع var قابلة للتغيير أو property ذات getter غير مستقر.

4. Not-null assertion !!

هو operator يجبر compiler على التعامل مع قيمة nullable باعتبارها non-nullable.

val length = phone!!.length

إذا كانت القيمة null، يحدث NullPointerException وقت التشغيل.

إذن !! لا يحل المشكلة؛ إنه ينقل مسؤولية التأكد من صحة الافتراض إلى المطور.

Kotlin Null Safety

مثال واقعي

لنفترض أن تطبيق مراسلة يعرض اسم الطرف الآخر وصورته الشخصية. الصورة اختيارية، لكن بيانات الحساب الأساسية يجب أن تكون موجودة.

data class UserProfile(
    val userId: String,
    val displayName: String,
    val avatarUrl: String?
)

يمكن التعامل مع الصورة دون اعتبار غيابها خطأ:

fun getAvatarLabel(profile: UserProfile): String {
    return profile.avatarUrl?.let {
        "Avatar available"
    } ?: "Default avatar"
}

لكن يجب التمييز بين ثلاث حالات:

  1. لا يوجد avatarUrl أصلًا.
  2. يوجد URL لكنه غير صالح.
  3. يوجد URL صالح لكن تحميل الصورة فشل بسبب الشبكة.

Null Safety تعالج الحالة الأولى على مستوى أنواع Kotlin، لكنها لا تعالج الحالتين الأخريين تلقائيًا.

هذه نقطة مهمة: nullability تصف إمكانية غياب القيمة، ولا تصف صلاحيتها أو صحتها التجارية.

البدائل

في Java يمكن استخدام Optional<T> في بعض عقود APIs لتمثيل احتمالية غياب قيمة، أو الاعتماد على null checks والـ annotations.

أما Kotlin فتدمج nullable types في نظام الأنواع، ولذلك تكون المعالجة جزءًا من طريقة كتابة التعبيرات نفسها.

في تطبيق Android، لا يوجد سبب لفرض Optional على جميع النماذج المكتوبة بـ Kotlin؛ استخدم nullable types وفق عقد البيانات، مع الانتباه إلى توافقها مع Java libraries.

أين يفشل

1. Null Safety لا تشمل Java تلقائيًا.

هذه أهم نقطة في التكامل بين اللغتين.

قد تستدعي Kotlin دالة Java لا تحتوي على nullability annotations:

public String getDisplayName() {
    return null;
}

عند استدعائها من Kotlin، قد يتعامل compiler مع نوع الإرجاع باعتباره String!.

يسمى هذا النوع Platform Type، وهو نوع مرن لا يحدد بوضوح هل القيمة nullable أم non-nullable.

يسمح ذلك بقدر أكبر من التوافق مع Java، لكنه يعني أن Kotlin لا تستطيع ضمان null safety عند هذا الحد الفاصل.

val name: String = javaUser.getDisplayName()

قد يقبل compiler هذا الإسناد، لكن إذا أعادت Java قيمة null فقد يظهر NullPointerException وقت التشغيل.

الحل هو وضع nullability contract واضح في Java APIs باستخدام annotations المناسبة، أو تحويل القيمة إلى nullable type فور دخولها إلى Kotlin.

2. استخدام !! كحل متكرر.

إذا وجدت !! في مسار تنفيذ عادي مثل تحميل بيانات المستخدم أو معالجة استجابة API، فغالبًا توجد مشكلة في تصميم عقد البيانات أو طريقة التعامل مع الفشل.

3. الخلط بين null وempty.

null و"" حالتان مختلفتان:

val a: String? = null
val b: String = ""

قد تكون القيمة موجودة لكنها فارغة، وهذا لا يسبب مشكلة nullability، لكنه قد يظل خطأً تجاريًا.

4. افتراض أن nullable يعني أن البيانات اختيارية تجاريًا.

قد تسمح قاعدة البيانات بقيمة فارغة، لكن النظام التجاري لا يسمح بها. يجب ألا تجعل نوع البيانات وحده هو مصدر الحقيقة لقواعد العمل.

عند التشخيص، راجع النوع الذي أعلنته Kotlin، ومصدر القيمة، وأي Java boundary عبر stack trace ورسالة الخطأ. ويمكنك أيضًا فحص نوع القيمة الذي يعرضه Android Studio عند الوقوف على المتغير.

قاعدة القرار

استخدم T? عندما يكون غياب القيمة جزءًا صحيحًا من عقد البيانات، واستخدم T عندما يجب أن تكون القيمة موجودة.

عند عبور Java APIs، لا تفترض أن null safety محفوظة تلقائيًا؛ حوّل Platform Types إلى أنواع Kotlin صريحة عند حدود النظام.

2.3 Java Interoperability

المشكلة

Android لا يبدأ من Kotlin فقط.

تاريخيًا، كُتبت معظم Android APIs والمكتبات الأساسية باستخدام Java، كما توجد مشاريع إنتاجية ضخمة ومكتبات داخلية تعتمد عليها.

إذا كانت Kotlin تتطلب إعادة كتابة كل Java code أو استبدال جميع المكتبات، لكانت كلفة تبنيها مرتفعة جدًا.

كان من الضروري أن تكون اللغة الجديدة قابلة للاندماج داخل مشاريع Java القائمة، وأن تسمح باستخدام المكتبات الحالية دون طبقة تحويل منفصلة لكل مكتبة.

كيف يعمل

النموذج الذهني

Kotlin/JVM وJava يستطيعان إنتاج JVM bytecode، وهو تمثيل وسيط للتعليمات البرمجية يمكن لبيئة JVM تنفيذه.

الآلية خطوة بخطوة

عند استخدام Java class من Kotlin:

  1. يقرأ Kotlin compiler معلومات الـ class من Java bytecode أو source المتاح.
  2. يتعرف على constructors وmethods وfields وtypes.
  3. يسمح باستدعائها باستخدام syntax الخاصة بـ Kotlin.
  4. يُنتج bytecode يمكن ربطه مع Java classes في مرحلة البناء.

مثلًا، يمكن أن تكون لديك Java class:

public class PriceFormatter {
    public String format(long amount) {
        return amount + " EGP";
    }
}

وتستدعيها من Kotlin مباشرة:

val formatter = PriceFormatter()
val label = formatter.format(15000)

لا تحتاج إلى adapter لمجرد أن إحدى اللغتين Java والأخرى Kotlin.

الاتجاه العكسي: Java تستدعي Kotlin

يمكن لملفات Java استدعاء Kotlin classes، لكن بعض خصائص Kotlin لا تظهر في Java بنفس الطريقة.

مثلًا، Kotlin تسمح بتعريف top-level function:

// CurrencyUtils.kt

fun formatAmount(amount: Long): String {
    return "$amount EGP"
}

تُتاح هذه الدالة لجهة Java من خلال class اصطناعية تمثل ملف Kotlin، ويكون اسمها الافتراضي مشتقًا من اسم الملف.

كما يمكن التحكم في طريقة ظهور بعض العناصر باستخدام annotations مثل:

  • @JvmStatic
  • @JvmOverloads
  • @JvmField
  • @JvmName

مثلًا:

@JvmOverloads
fun formatAmount(
    amount: Long,
    currency: String = "EGP"
): String {
    return "$amount $currency"
}

تساعد @JvmOverloads على توليد overloads مناسبة كي يستطيع Java استدعاء الدالة باستخدام عدد أقل من المعلمات.

وهناك فرق مهم آخر: عند استدعاء Java لكود Kotlin، يمكن لـ Java تمرير null إلى parameter معلن في Kotlin على أنه non-nullable؛ لذلك يولّد Kotlin compiler runtime checks عند حدود الاستدعاءات المناسبة، لمنع استمرار القيمة الفارغة إلى داخل الكود الذي يفترض أنها غير فارغة.

هذه checks لا تعني أن جميع Java/Kotlin boundaries أصبحت آمنة تلقائيًا، لكنها تقلل مساحة انتشار الخطأ. Calling Java from Kotlin

مثال واقعي

لنفترض أن تطبيقًا مصرفيًا يحتوي على مكتبة Java داخلية مسؤولة عن تشفير بعض البيانات.

بدل إعادة كتابة المكتبة، يمكنك استدعاء API مباشرة:

البدائل

هناك ثلاثة أساليب عملية للتعامل مع مشروع يعتمد على Java:

  • الاستمرار في Java عندما تكون التكلفة والفائدة لا تبرران التغيير.
  • استخدام Kotlin تدريجيًا مع بقاء Java libraries والـ modules القديمة.
  • إعادة كتابة وحدات محددة بـ Kotlin عندما تحتاج إلى تبسيطها أو تطويرها بشكل مستمر.

لا يتطلب أي من هذه الخيارات أن يكون المشروع كله بلغة واحدة.

أين يفشل

1. افتراض أن التكامل يعني تطابق اللغتين.

هناك اختلافات في طريقة تمثيل properties وtop-level functions وdefault parameters وextension functions.

مثلًا، extension function في Kotlin لا تتحول إلى instance method حقيقية داخل Java class التي توسعها؛ بل تُمثّل عادةً كدالة static تتلقى الـ receiver كمعلمة.

لذلك لا تفترض أن كل syntax في Kotlin سيكون متاحًا بنفس الشكل لمستهلك Java.

2. إهمال nullability annotations.

إذا كانت Java APIs لا تصرح بوضوح عن nullability، قد تظهر Platform Types وتسمح بتمرير قيم تسبب أخطاء runtime.

3. تغيير API تستخدمه Java دون مراجعة توافقه.

قد يؤدي تعديل Kotlin class إلى تغيير شكل الـ bytecode أو الـ signatures التي تعتمد عليها Java callers.

خصوصًا عند استخدام:

  • Top-level declarations.
  • Default parameters.
  • Properties.
  • Companion objects.
  • Generic types.

راجع الـ generated API أو استخدم annotations المناسبة عندما تكون المكتبة مصممة ليستهلكها كود Java أيضًا.

4. نسيان Kotlin Standard Library.

هي مكتبة توفر الوظائف الأساسية التي تعتمد عليها برامج Kotlin، مثل collections functions وبعض الـ utility APIs.

تحتاج تطبيقات Kotlin/JVM عادةً إلى تضمين المكتبة المناسبة ضمن dependencies حتى تعمل أجزاء Kotlin التي تعتمد عليها.

قاعدة القرار

عامل Java وKotlin على أنهما لغتان يمكنهما المشاركة في النظام نفسه، وليس مشروعين منفصلين.

عند تصميم Kotlin APIs مخصصة لكي تستدعيها Java code، راجع شكل الـ generated bytecode وannotations والـ nullability، ولا تعتمد على أن جميع خصائص Kotlin ستظهر في Java تلقائيًا.

2.4 Type Inference

المشكلة

في لغة ذات static typing، تحتاج المتغيرات والمعلمات وقيم الإرجاع إلى أنواع محددة.

لكن كتابة النوع في كل تعبير عندما يكون واضحًا من السياق تنتج تكرارًا لا يضيف كثيرًا من المعلومات.

في الوقت نفسه، التخلص من الأنواع تمامًا سيؤدي إلى فقدان جزء مهم من الأمان الذي يوفره compiler.

المطلوب هو الاحتفاظ بـ static typing، مع السماح للغة باستنتاج النوع عندما تكون الأدلة كافية.

كيف يعمل

النموذج الذهني

Type Inference هي قدرة compiler على استنتاج النوع من القيم والتعبيرات والسياق، بدل إجبارك على كتابته صراحةً في كل مرة.

لا تعني أن Kotlin لغة dynamically typed.

انظر إلى المثال:

val orderCount = 15
val totalAmount = 24500L
val currency = "EGP"

الـ compiler يستنتج الأنواع التالية:

orderCount   -> Int
totalAmount  -> Long
currency     -> String

تظل الأنواع ثابتة بعد انتهاء compilation.

لا يمكن مثلًا إسناد String إلى orderCount:

orderCount = "Fifteen"

وهناك مشكلة أخرى في هذا المثال: orderCount معرّف باستخدام val، ولذلك لا يمكن إعادة إسناد أي قيمة جديدة له أصلًا.

الآلية الداخلية

يحلل compiler التعبير ويستخرج المعلومات المتاحة عن نوع القيمة، ثم يستخدمها للتحقق من بقية العمليات.

كما يمكنه استنتاج أنواع generic arguments في حالات كثيرة.

val prices = listOf(15000L, 22000L, 31000L)

يستنتج أن النوع هو:

List<Long>

ويمكن أيضًا استنتاج نوع إرجاع دالة من expression body:

fun calculateDiscount(
    price: Long,
    percentage: Double
) = (price * percentage / 100).toLong()

نوع الإرجاع هنا Long.

لكن يجب أن تعرف أن inference له حدود؛ فمثلًا، الدوال ذات block body تحتاج عادةً إلى تحديد return type صراحةً:

fun calculateDiscount(
    price: Long,
    percentage: Double
): Long {
    return (price * percentage / 100).toLong()
}

هذا ليس تناقضًا، بل اختلاف في قواعد استنتاج أنواع الدوال.

يستخدم compiler أيضًا المعلومات الناتجة عن شروط التنفيذ، ويمكن أن يستفيد منها في smart casts وgeneric type inference.

Kotlin Type Inference

مثال واقعي

لنفترض أن تطبيقًا يعرض قائمة المدفوعات التي استعادها Repository:

val payments = paymentRepository.getPayments()

إذا كان return type الخاص بالدالة هو:

fun getPayments(): List<Payment>

فلا تحتاج إلى تكرار النوع عند إنشاء المتغير.

يستطيع Android Studio أيضًا استخدام المعلومات المستنتجة لإظهار الدوال والـ properties المتاحة وإكمال الكود والتحقق من النوع أثناء الكتابة.

لكن عند تعريف API عامة داخل Repository، يكون توضيح النوع غالبًا أفضل:

fun getPayments(): List<Payment> {
    // ...
}

لأن return type جزء من العقد الذي تعتمده الطبقات الأخرى.

البدائل

يمكنك استخدام explicit type declarations في كل مكان، وهو أسلوب يوفر وضوحًا أكبر في بعض السياقات، لكنه يزيد التكرار.

ويمكنك أيضًا الاعتماد على inference محليًا، مع الاحتفاظ بتحديد الأنواع في حدود الدوال العامة والعقود المعمارية.

هذا المزيج غالبًا هو الأنسب لمشاريع Android المتوسطة والكبيرة.

أين يفشل

1. الاعتقاد أن غياب النوع يعني غياب static typing.

val amount = 500L

النوع معروف للـ compiler، حتى لو لم تكتبه.

2. إنشاء تعبيرات معقدة يصعب معرفة نوعها.

خصوصًا عند استخدام generics وlambdas وnested collection operations.

val result = orders
    .filter { it.isPaid }
    .groupBy { it.customerId }
    .mapValues { (_, values) -> values.sumOf { it.total } }

إذا أصبح النوع غير واضح أثناء القراءة أو debugging، أضف annotation صريحة أو قسّم التعبير إلى متغيرات بأسماء ذات معنى.

3. ترك الأنواع غامضة عند حدود Architecture.

في الأنظمة متعددة الطبقات، يجب أن يكون العقد بين Repository وViewModel وUI مفهومًا ومستقرًا.

لا تجعل سهولة inference سببًا لعدم توضيح الأنواع التي تعتمد عليها طبقات متعددة.

قاعدة القرار

استخدم inference عندما يكون النوع واضحًا محليًا، واكتب الأنواع صراحةً عندما يكون ذلك مهمًا لفهم API أو الحفاظ على وضوح الـ architecture.

3. Where Kotlin runs

3.1 المشكلة

عندما طُورت Kotlin، لم يكن الهدف حصرها في Android أو ربطها بنظام تشغيل واحد.

المشكلة الهندسية التي تحاول معالجتها هنا هي تكرار كتابة نفس المنطق في تطبيقات تعمل على منصات مختلفة.

لنفترض أن شركة تملك:

  • تطبيق Android.
  • تطبيق iOS.
  • Backend مسؤولًا عن المصادقة وتسعير المنتجات.
  • تطبيق Web لإدارة العمليات.

إذا كان لكل منصة تنفيذ مستقل لقواعد العمل، فقد تظهر اختلافات تدريجية في حساب الأسعار والتحقق من المدخلات والتعامل مع الحالات الاستثنائية.

من جهة أخرى، استخدام كود واحد بالكامل على كل المنصات ليس ممكنًا دائمًا؛ لأن كل منصة لها APIs وبيئة تشغيل وتجربة استخدام مختلفة.

Kotlin تقدم خيارات مختلفة بحسب مقدار الكود الذي تريد مشاركته.

3.3 مثال واقعي

لنفترض أن لديك تطبيقًا مصرفيًا يعمل على Android وiOS.

تحتاج المنصتان إلى تنفيذ القواعد التالية:

  • حساب رسوم التحويل.
  • التحقق من حدود المبالغ.
  • تحليل حالة العملية المصرفية.
  • تطبيق قواعد التحقق من بيانات التحويل.

إذا كانت هذه القواعد متطابقة بين المنصتين، يمكن وضعها في shared Kotlin module.

data class TransferRequest(
    val amountMinor: Long,
    val availableBalanceMinor: Long
)

fun validateTransfer(
    request: TransferRequest
): Boolean {
    return request.amountMinor > 0 &&
        request.amountMinor <= request.availableBalanceMinor
}

يمكن استخدام هذه القاعدة في Android وiOS بدل إعادة تنفيذها مرتين.

لكن لا ينبغي أن تكون هذه الوظيفة وحدها هي المرجع النهائي لاعتماد تحويل مالي حقيقي؛ فالـ Backend يجب أن يتحقق من الرصيد والصلاحيات والقواعد الأمنية بنفسه، لأن تطبيق العميل يعمل في بيئة لا تتحكم فيها الشركة.

هذا مثال على قرار هندسي مهم: مشاركة منطق التطبيق لتحسين الاتساق لا تعني نقل مسؤولية الأمان من الخادم إلى العميل.

الاختيار لا يعتمد على عدد المنصات فقط؛ بل على نوع الكود الذي تريد مشاركته، ومتطلبات الأداء، ودرجة اعتمادك على APIs الأصلية.

3.5 أين يفشل

1. الاعتقاد أن KMP تعني Write Once, Run Everywhere دون قيود.

قد تعتمد مكتبة على Android API لا توجد على iOS.

عند نقلها إلى commonMain، ستواجه مشكلة لأن الكود المشترك لا يستطيع الاعتماد على API متاحة لهدف واحد فقط.

الحل هو فصل واجهة الاستخدام العامة عن التنفيذ الخاص بكل منصة، وعدم وضع platform-specific dependencies في الكود المشترك دون مبرر.

2. الخلط بين KMP وCompose Multiplatform.

قد يحتاج المشروع إلى مشاركة Business Logic فقط، بينما تكون الواجهة أصلية لكل نظام.

إدخال UI framework مشترك في هذه الحالة قد يضيف كلفة لا تحتاج إليها.

3. الاعتقاد أن Kotlin تعمل بنفس الطريقة في كل target.

هناك اختلافات في المكتبات المتاحة وآليات إدارة الذاكرة والتكامل مع النظام المستهدف.

الكود الذي يعمل على JVM قد يعتمد على APIs غير موجودة في Kotlin/Native أو غير متاحة في commonMain.

4. الاعتقاد أن مشاركة الكود تضمن التطابق التشغيلي.

حتى لو كانت قواعد العمل مشتركة، تظل هناك اختلافات محتملة في الشبكة والتخزين والواجهات ودورة الحياة وإدارة الموارد.

3.6 قاعدة القرار

في Android، ركّز أولًا على فهم Kotlin/JVM وسلسلة التنفيذ عبر DEX وART.

انتقل إلى KMP عندما يكون لديك سبب واضح لمشاركة منطق بين منصات متعددة، وابدأ بالمكونات المستقلة عن النظام بدل محاولة مشاركة التطبيق بالكامل من البداية.

4. Kotlin and Java compared

4.1 المشكلة

من الأخطاء الشائعة عند تعلم Kotlin اعتبارها Java مختصرة، أو الاعتقاد بأن تعلم Java لم يعد مفيدًا بعد الانتقال إلى Kotlin.

كلا التصورين غير دقيق.

Kotlin وJava لغتان مختلفتان، لكنهما تتكاملان بشدة داخل JVM ecosystem، ولذلك يحتاج مهندس Android إلى فهم نقاط التشابه والاختلاف بينهما.

  2. Interoperability.

4.2 كيف يعمل

أولًا: Syntax

لنفترض أننا نريد تمثيل عملية دفع.

باستخدام Java الحديثة التي تدعم record:

public record Payment(
    String id,
    long amountMinor
) {}

وباستخدام Kotlin:

data class Payment(
    val id: String,
    val amountMinor: Long
)

كلاهما يهدف إلى تقليل الكود المتكرر عند تعريف نموذج بيانات، لكن لكل منهما قواعد وخصائص مختلفة.

في Kotlin ستلاحظ الاختلافات التالية:

1. Variable Declaration

في Kotlin:

val orderId = "ORD-105"
var status = "PENDING"

أما في Java:

final String orderId = "ORD-105";
String status = "PENDING";

val تقابل مفهوم reference غير القابل لإعادة الإسناد، بينما var تسمح بإعادة الإسناد.

Java لديها أيضًا var للاستنتاج المحلي للأنواع منذ Java 10، لكنها لا تماثل var في Kotlin تمامًا؛ لأنها لا تعني قابلية إعادة الإسناد أو عدمها، بل تتعلق باستنتاج النوع المحلي.

2. Nullability

في Kotlin:

val customerName: String
val phoneNumber: String?

في Java، يمكن استخدام annotations لتوضيح احتمالية null:

@NotNull String customerName;
@Nullable String phoneNumber;

لكن nullability ليست جزءًا أصيلًا من Java type system بالطريقة نفسها التي هي عليها في Kotlin.

لذلك تستطيع Kotlin فرض قيود nullability أثناء compilation بصورة أكثر مباشرة.

3. Default Parameters

في Kotlin:

fun calculateTotal(
    price: Long,
    fee: Long = 0
): Long {
    return price + fee
}

يمكن استدعاؤها دون تمرير fee.

أما Java فلا توفر default parameters بالصيغة نفسها، ويمكن استخدام overloads أو Builder pattern لتحقيق نتيجة مشابهة.

4. Named Arguments

في Kotlin:

calculateTotal(
    price = 15000,
    fee = 500
)

تساعد named arguments في توضيح معنى القيم، خصوصًا عندما يكون هناك عدد كبير من parameters لها النوع نفسه.

Java لا توفر named arguments بهذه الصيغة.

5. Expression-oriented Syntax

في Kotlin، يمكن استخدام if وwhen كـ expressions تنتج قيمًا:

val deliveryMessage = if (isDelivered) {
    "Delivered"
} else {
    "In transit"
}

في Java، يمكن استخدام ternary operator أو switch expressions في الإصدارات الحديثة بحسب الحالة.

إذن Java الحديثة ليست ثابتة عند مستوى Java القديمة؛ فقد تطورت وأصبحت تدعم خصائص مثل records وvar وswitch expressions وpattern matching.

الاختلاف ليس أن كل ميزة موجودة في Kotlin غائبة تمامًا عن Java، بل أن طريقة التعبير عن المنطق والعقود تختلف بين اللغتين. Comparison to Java

ثانيًا: Interoperability

هذا هو أحد أهم أسباب ملاءمة Kotlin لتطوير Android.

عندما تكتب Kotlin/JVM وJava داخل المشروع نفسه، لا تحتاج إلى ترجمة كل لغة إلى لغة الأخرى.

كل منهما يمكن أن ينتج JVM bytecode، ويمكن للكود الناتج استدعاء الـ classes والـ methods الموجودة في الآخر.

مثلًا، قد يحتوي المشروع على:

لكن التوافق لا يعني أن Java ترى جميع عناصر Kotlin بنفس syntax.

مثلًا:

  • Kotlin properties تظهر لجهة Java من خلال getter وsetter المناسبين.
  • Top-level functions تظهر من خلال class اصطناعية تمثل ملف Kotlin.
  • Default parameters تحتاج إلى overloads مناسبة كي تستخدمها Java بسهولة.
  • Extension functions لا تتحول إلى member methods داخل Java classes.

ولهذا توجد @JvmStatic و@JvmOverloads و@JvmName وغيرها للتحكم في شكل بعض declarations على مستوى JVM.

عند اختيار اللغة لمشروع Android:

Java مناسبة عندما يكون المشروع قائمًا عليها، أو عندما يعتمد الفريق بدرجة كبيرة على خبرات وأدوات ومكتبات Java.

Kotlin مناسبة للتطوير الحديث في Android، وخصوصًا عند استخدام Jetpack Compose والمكتبات الحديثة المصممة بأسلوب Kotlin-first.

Mixed Java/Kotlin مناسبة عندما تريد تحديث المشروع تدريجيًا دون دفع تكلفة إعادة الكتابة دفعة واحدة.

من الناحية العملية، لا يوجد تعارض معماري بين استمرار استخدام Java في بعض الطبقات وكتابة طبقات أخرى بـ Kotlin.

4.5 أين يفشل

1. توقع أن Java وKotlin تنتجان دائمًا نفس bytecode.

ليستا compilerين متطابقين، وقد تختلف طريقة تمثيل بعض خصائص اللغة والمكتبات في bytecode.

لا تبنِ قرارات الأداء على عدد الأسطر أو شكل syntax.

2. الاعتقاد أن Kotlin أسرع تلقائيًا من Java.

لا توجد قاعدة عامة تقول إن مجرد تحويل الكود من Java إلى Kotlin سيجعل التطبيق أسرع.

الأداء يعتمد على العمليات المنفذة، والـ bytecode الناتج، وعمليات JIT/AOT والتحسينات التي تحدث أثناء التنفيذ.

يمكن أن يكون كود Java أسرع من كود Kotlin سيئ التصميم، والعكس صحيح.

3. التعامل مع Java APIs كما لو كانت مكتوبة بـ Kotlin.

قد تكون Java method ترجع null دون توضيح ذلك في توقيعها.

المؤشر المهم هنا هو Platform Type، وليس مجرد أن الكود اجتاز compilation.

4. تجاهل API Compatibility عند بناء مكتبة مشتركة.

قد يحتوي Kotlin class على public declarations يستخدمها Java consumers، وبالتالي يجب مراجعة شكل الـ generated API عند تغييرها.

5. افتراض أن استخدام Kotlin يلغي الحاجة إلى فهم Java.

هذا خطأ عملي في Android؛ فكثير من APIs والمكتبات والأمثلة القديمة ما زالت تستخدم Java.

4.6 قاعدة القرار

تعامل مع Kotlin باعتبارها اللغة الأساسية المناسبة لتطوير Android الحديث، ومع Java باعتبارها جزءًا مستمرًا ومهمًا من بيئة Android وJVM.

لا تخلط بين اختلاف syntax واختلاف runtime، ولا تعِد كتابة Java code إلا عندما توجد فائدة هندسية واضحة.

5.1 المشكلة

Kotlin لغة تتطور باستمرار.

تظهر مع الوقت تحسينات في compiler وtype inference وlanguage features والمكتبات والأدوات.

لكن في مشروع Android، تحديث Kotlin ليس مجرد تغيير رقم الإصدار؛ لأن عملية البناء تعتمد على عدة مكونات يجب أن تكون متوافقة مع بعضها.

قد تستخدم Kotlin version أحدث، لكن Android Gradle Plugin أو أحد compiler plugins في المشروع لا يدعمها بالصورة المطلوبة.

في K2، أعادت JetBrains بناء Frontend باستخدام بنية أكثر توحيدًا وغنى بالمعلومات الدلالية.

هذه البنية مسؤولة عن أمور مثل:

  • Semantic analysis.
  • Call resolution.
  • Type inference.
  • اكتشاف الأخطاء والتحقق من صحة التعبيرات.

النتيجة هي تحليل أكثر اتساقًا وتحسينات في قدرات compiler وأدائه أثناء عملية البناء.

هذا لا يعني أن K2 قدم لغة Kotlin جديدة مستقلة، ولا أنه استبدل الـ runtime المستخدم على Android.

5.3 مثال واقعي

لنفترض أن لديك تطبيق Android مبنيًا باستخدام Kotlin 1.9، وتريد تحديثه إلى Kotlin 2.4.

Kotlin 1.9 -> Kotlin 2.4

لكن القرار الفعلي يحتاج إلى مراجعة أكثر من ملف.

افترض أن المشروع يستخدم:

  • Android Gradle Plugin.
  • Kotlin Gradle Plugin.
  • Jetpack Compose.
  • Kotlin Serialization.
  • KSP.

عند تحديث Kotlin، يجب التحقق من توافق plugins المعتمدة على compiler APIs، وليس فقط التأكد من أن ملفات .kt لا تحتوي على أخطاء.

5.4 البدائل

عندما تتعامل مع تحديث Kotlin، توجد عدة استراتيجيات:

1. Stable Kotlin Version

استخدام إصدار مستقر ومدعوم من أدوات المشروع.

هذا هو الخيار الطبيعي للتطبيقات الإنتاجية.

2. Early Access Preview (EAP)

EAP هي إصدارات تجريبية متاحة قبل الإصدار المستقر، وتُستخدم لاختبار الميزات الجديدة وإرسال الملاحظات إلى المطورين.

يمكن استخدامها في مشروع تجريبي أو بيئة منفصلة للتحقق من التوافق القادم.

لا تجعل إصدار EAP اعتمادًا أساسيًا في تطبيق إنتاجي إلا مع وجود سبب وخطة واضحة للمخاطر.

3. تأجيل الترقية

قد يكون البقاء على إصدار أقدم مناسبًا عندما تكون تكلفة الترقية أكبر من فائدتها الفورية، بشرط أن يظل الإصدار مدعومًا ومتوافقًا مع احتياجات المشروع.

لكن يجب عدم تحويل التأجيل إلى تجميد دائم؛ لأن ذلك يزيد لاحقًا كلفة تحديث الأدوات والمكتبات ومعالجة التوافق.

5.5 أين يفشل

1. تحديث Kotlin دون فحص AGP.

قد تكون Kotlin version صحيحة من ناحية اللغة، لكن إصدار Android Gradle Plugin أو أدوات D8/R8 الموجودة في المشروع لا يوفر التوافق المطلوب.

التشخيص: راجع رسالة الخطأ أولًا، ثم مصفوفة التوافق الرسمية الخاصة بإصدار Kotlin وAGP وD8/R8.

2. الخلط بين Kotlin compiler وAndroid runtime.

K2 لا يستبدل ART.

إذا حدث crash على جهاز المستخدم، فلا تفترض أن K2 هو المسؤول لمجرد أنك انتقلت إليه؛ افحص stack trace والـ generated artifacts والمشكلة الفعلية.

3. الاعتقاد أن K2 سيجعل التطبيق أسرع تلقائيًا.

التحسين الأساسي لـ K2 يتعلق بالـ compiler وتجربة التطوير وعملية التحليل والبناء.

لا تستنتج من ذلك أن عملية عرض الشاشة أو تنفيذ طلب الشبكة ستصبح أسرع بمجرد تحديث compiler.

لتحليل أداء التطبيق، استخدم Android Profiler وقياسات الأداء الفعلية.

4. تجاهل Compiler Plugins.

قد يكون Kotlin compiler متوافقًا مع مشروعك، بينما أحد plugins يحتاج إلى إصدار مختلف.

افحص توافق KSP وSerialization وCompose compiler وأي compiler plugins أخرى مستخدمة.

5. استخدام أحدث إصدار دون سبب أو خطة.

التحديث ليس هدفًا مستقلًا؛ الهدف هو الاستفادة من التحسينات مع الحفاظ على استقرار عملية البناء وسلوك التطبيق.

6. عدم التمييز بين Language Version وAPI Version.

Language Version تحدد مستوى ميزات اللغة والتوافق اللغوي الذي يسمح به compiler.

أما API Version فتحدد مجموعة إصدارات Kotlin APIs المتاحة للاستخدام، وهو أمر مهم عند تطوير مكتبات يجب أن تعمل مع إصدارات أقدم من Kotlin.

هذان الإعدادان ليسا نفس رقم إصدار Kotlin Gradle Plugin بالضرورة.

5.6 قاعدة القرار

استخدم Stable Kotlin releases في تطبيقات الإنتاج، وتحقق من توافق Kotlin Compiler وKotlin Gradle Plugin وGradle وAGP وD8/R8 والـ compiler plugins قبل التحديث.

تعامل مع K2 باعتباره compiler architecture الحديثة والمستقرة، وليس runtime جديدًا أو تحسينًا تلقائيًا لأداء التطبيق بعد تشغيله.

6.3 اختبار الفهم الهندسي

مراجعة الفهم

  1. لديك Java API ترجع String دون Nullability Annotation. Kotlin تسمح باستدعاء length مباشرة، لكن التطبيق يتعرض أحيانًا إلى NullPointerException. ما التفسير الأدق؟

    1. Kotlin compiler لا يدعم Null Safety
    2. القيمة من Java قد تكون Platform Type، ولذلك لا يضمن compiler عدم كونها null
    3. ART لا يستطيع تنفيذ Kotlin String

    الإجابة الصحيحة: القيمة من Java قد تكون Platform Type، ولذلك لا يضمن compiler عدم كونها null.

    Platform Types تسمح بمرونة عند حدود Java، لكنها لا تمنح ضمان null safety. يجب توضيح nullability أو معالجة القيمة عند الحد الفاصل.

  2. لديك val يشير إلى MutableList. هل يمكن إضافة عنصر إليها؟

    1. لا، لأن val تعني أن الكائن immutable
    2. نعم، لأن val تمنع إعادة إسناد المرجع ولا تمنع تعديل الكائن المشار إليه
    3. نعم فقط إذا كانت القائمة فارغة

    الإجابة الصحيحة: نعم، لأن val تمنع إعادة إسناد المرجع ولا تمنع تعديل الكائن المشار إليه.

    عدم قابلية إعادة الإسناد ليست هي immutability. نوع الكائن نفسه هو الذي يحدد إمكان تعديل محتوياته.

  3. هل Kotlin على Android تعمل داخل JVM تقليدية؟

    1. نعم، التطبيق يشغّل JVM كاملة على الجهاز
    2. لا، Kotlin تُترجم إلى JVM bytecode ثم DEX وينفذ ART النتيجة
    3. لا، Kotlin تتحول دائمًا مباشرة إلى Native Binary

    الإجابة الصحيحة: لا، Kotlin تُترجم إلى JVM bytecode ثم DEX وينفذ ART النتيجة.

    Android يستخدم مسار JVM bytecode ثم DEX، والـ runtime هو ART.

  4. لماذا لا يكفي تحديث Kotlin Compiler وحده عند ترقية إصدار المشروع؟

    1. لأن Kotlin لا تدعم Gradle
    2. لأن AGP وD8/R8 وCompiler Plugins قد تحتاج إلى إصدارات متوافقة
    3. لأن كل تحديث Kotlin يتطلب إعادة كتابة Java

    الإجابة الصحيحة: لأن AGP وD8/R8 وCompiler Plugins قد تحتاج إلى إصدارات متوافقة.

    عملية بناء Android تتكون من عدة أدوات مترابطة؛ يجب التحقق من مصفوفة التوافق كاملة.

  5. ما الفرق الجوهري بين KMP وCompose Multiplatform؟

    1. لا يوجد أي فرق
    2. KMP تشارك الكود، بينما Compose Multiplatform تتيح مشاركة UI أيضًا
    3. KMP خاصة بـ iOS فقط

    الإجابة الصحيحة: KMP تشارك الكود، بينما Compose Multiplatform تتيح مشاركة UI أيضًا.

    KMP لا تشترط مشاركة الواجهات؛ يمكن مشاركة Business Logic مع الاحتفاظ بواجهات أصلية.
