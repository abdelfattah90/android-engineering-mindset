Introduction to Kotlin العودة إلى الخطة

Introduction to Kotlin - مقدمة إلى Kotlin

تبدأ دراسة Kotlin بفهم المشكلة التي تحاول حلها، لا بحفظ syntax الخاص بها. بعد ذلك نربط خصائص اللغة بكيفية كتابة كود أكثر أمانًا وقابلية للصيانة، ثم نفهم أن Kotlin ليست مرتبطة بـ Android أو حتى بـ JVM وحدها. هذا يقودنا إلى فهم علاقتها بـ Java، وهي علاقة تكامل أكثر منها علاقة استبدال. وأخيرًا، نفصل بين تطور اللغة نفسها وتطور compiler وأدوات بناء تطبيقات Android، لأن الخلط بينها يسبب مشكلات فعلية عند تحديث المشاريع.

1. What Kotlin Is and the Problems It Was Designed to Solve

1.1 المشكلة (Problem)

قبل Kotlin، كانت Java اللغة الأساسية المستخدمة في تطوير Android، وما زالت لغة مدعومة بالكامل حتى اليوم.

Java لغة قوية ومستقرة، ولديها ecosystem ضخم، لكن تطوير تطبيقات كبيرة بها يواجه بعض الاحتكاكات المتكررة:

أولًا: Verbose Syntax

بعض المهام البسيطة تحتاج إلى قدر كبير من الكود المتكرر.

مثلًا، إنشاء class لتمثيل تحويل مالي قد يتطلب كتابة constructor وgetters وequals() وhashCode() وtoString() يدويًا أو الاعتماد على أدوات تولّدها.

عندما يتكرر هذا الأسلوب في مئات الـ models، يصبح جزء من الكود مسؤولًا عن تمثيل البيانات بدلًا من التعبير عن منطق التطبيق.

ثانيًا: Null-related errors

في Java، يمكن أن يكون أي reference تقريبًا null، ولا يعبّر نوع المتغير نفسه بالضرورة عن إمكانية احتوائه على null.

قد تستقبل دالة كائنًا، وتفترض أنه موجود، ثم تفشل أثناء التنفيذ بسبب عدم وجوده.

String name = user.getName();
int length = name.length();

إذا أعادت getName() القيمة null، سيحدث NullPointerException.

المشكلة ليست في وجود null بحد ذاته، بل في أن العقد الذي يحدد هل القيمة اختيارية أم إلزامية لا يكون واضحًا دائمًا في type system.

ثالثًا: التعبير عن منطق أكثر باستخدام constructs أبسط

مع توسع التطبيقات، تظهر احتياجات متكررة مثل تحويل البيانات، والتعامل مع collections، وتمرير السلوك كقيمة، وبناء APIs معبّرة.

توفر Java هذه الإمكانيات بدرجات مختلفة، لكن Kotlin صُممت لتجعلها جزءًا طبيعيًا من اللغة.

إذًا لم يكن الهدف إنشاء Java أخرى، ولا التخلص من مكتبات Java، بل تقديم لغة عملية وحديثة تقلل الاحتكاك في التطوير اليومي وتحافظ على إمكانية العمل مع النظام البيئي الموجود.

1.2 كيف تعمل (How It Works)

Mental Model

فكّر في Kotlin باعتبارها لغة تصف بها البرنامج بطريقة أكثر تعبيرًا، ثم يحوّل compiler هذا الوصف إلى صيغة قابلة للتنفيذ على المنصة المستهدفة.

Kotlin ليست framework، وليست Android SDK، وليست runtime مستقلة في كل الحالات.

هي لغة برمجة لها compiler وstandard library، وتستطيع استهداف أكثر من بيئة تشغيل.

تتكون الصورة الذهنية من ثلاث طبقات:

  1. Language: القواعد التي تكتب بها الكود، مثل classes وfunctions وtypes.
  2. Compiler: الأداة التي تحلل الكود وتتأكد من صحته وتحوّله إلى صيغة تناسب المنصة المستهدفة.
  3. Runtime: البيئة والمكتبات التي توفر خدمات التنفيذ، مثل إدارة الذاكرة وتنفيذ العمليات والتعامل مع الأنظمة.

في Android، ستكتب Kotlin، لكن التطبيق لن يحتاج إلى Kotlin VM خاصة به.

سنفصل مسار التنفيذ في موضوع منصات Kotlin لاحقًا.

الآلية الداخلية

عند كتابة:

data class Payment(
    val id: String,
    val amountMinor: Long
)

فإن Kotlin compiler يتعرف على تعريف البيانات ويولّد العمليات المرتبطة به تلقائيًا.

data class هي نوع من classes مخصص لتمثيل البيانات، ويولّد compiler له عمليات مثل equals() وhashCode() وtoString() وcopy().

الفائدة ليست مجرد تقليل عدد الأسطر؛ بل تقليل فرص نسيان سلوك متكرر أو كتابته بطريقة غير متسقة.

أما بالنسبة إلى type checking، فيحلل compiler أنواع القيم والعمليات قبل إنشاء الناتج التنفيذي. وبالتالي يستطيع اكتشاف كثير من الأخطاء قبل تشغيل التطبيق.

لكن يجب الانتباه إلى أن اكتشاف الأخطاء أثناء compilation لا يعني أن compiler قادر على اكتشاف كل أخطاء التطبيق. أخطاء business logic، وحالات الشبكة، ومشكلات التزامن، وسوء استخدام Android APIs تظل ممكنة.

1.3 مثال واقعي (Real-world Example)

لنفترض أنك تعمل على تطبيق مصرفي يحتوي على بيانات التحويلات المالية.

تحتاج إلى تمثيل تحويل له مبلغ ومستفيد وملاحظة اختيارية.

في Kotlin:

data class Transfer(
    val beneficiaryId: String,
    val amountMinor: Long,
    val note: String? = null
)

لاحظ ثلاثة قرارات:

  • val يجعل إعادة إسناد الخاصية ممنوعًا بعد إنشائها.
  • String? يعبّر بوضوح عن إمكانية عدم وجود ملاحظة.
  • data class يوفر السلوك المعتاد لتمثيل البيانات دون كتابته يدويًا.

يمكنك بناء نسخة معدّلة من الكائن بسهولة:

val updatedTransfer = transfer.copy(
    note = "Monthly payment"
)

هذه الطريقة تجعل تمثيل البيانات أكثر وضوحًا، وتقلل الحاجة إلى كتابة constructors ونسخ الحقول يدويًا.

لكن لا تستنتج أن استخدام Kotlin يجعل الكائن immutable بالكامل. فـ val يمنع إعادة إسناد reference، ولا يمنع بالضرورة تعديل object الذي يشير إليه.

1.4 البدائل (Alternatives)

أمامك ثلاثة اتجاهات عملية:

Java فقط: مناسب عندما تعمل على codebase قائم ومستقر بلغة Java، أو عندما تكون هناك قيود مؤسسية أو تقنية تمنع إدخال Kotlin.

Kotlin فقط: مناسب للمشروعات الجديدة التي لا تحتاج إلى التعايش مع قدر كبير من Java code، ويركز على توحيد أسلوب التطوير.

Kotlin وJava معًا: مناسب للمشروعات القائمة التي تريد تحديثها تدريجيًا دون إعادة كتابة التطبيق بالكامل.

الاختيار الثالث مهم جدًا في Android؛ لأن Kotlin تستطيع استدعاء Java، وJava تستطيع استدعاء Kotlin، وبالتالي يمكن إدخال اللغة الجديدة module بعد module أو feature بعد feature.

1.5 أين يفشل (Failure Modes)

من الأخطاء الشائعة الاعتقاد بأن Kotlin صُممت خصيصًا لـ Android.

هذا غير صحيح. Kotlin لغة عامة الاستخدام، ويمكن استخدامها على الخادم والويب وسطح المكتب والأنظمة متعددة المنصات.

خطأ آخر هو الاعتقاد بأن قلة الأسطر تعني بالضرورة كودًا أفضل. يمكن كتابة Kotlin مختصرة جدًا، لكنها صعبة القراءة والصيانة.

مثلًا:

val result = items.mapNotNull { it.value?.trim()?.takeIf(String::isNotEmpty) }

قد تكون هذه الصيغة مناسبة في سياقها، لكن تكديس العمليات داخل expression واحد ليس دائمًا الخيار الأفضل.

أعراض المشكلة: صعوبة فهم الكود، وتعقيد debugging، وكثرة التغييرات التي تؤثر في أجزاء غير واضحة.

التشخيص: اسأل هل يعبر الكود عن business rule بوضوح، أم أنه يستغل إمكانيات اللغة دون مراعاة قابلية القراءة؟

1.6 قاعدة القرار (Decision Rule)

استخدم Kotlin في تطوير Android الجديد لأنها اللغة الموصى بالبدء بها في نهج Android Kotlin-first، مع الاستفادة من تكاملها مع Java عند التعامل مع المشروعات والمكتبات القائمة.

لا تختَر Kotlin لمجرد أنها أحدث من Java؛ اخترها لأن خصائصها تساعد على التعبير عن قواعد التطبيق وقيوده بصورة أوضح.

2. Core Language Traits

الموضوعات الأربعة التالية ليست مجرد تحسينات في syntax؛ إنها تؤثر مباشرة في طريقة تصميم interfaces والـ models والتعامل مع البيانات.

2.1 المشكلة (Problem)

عند بناء تطبيق Android، تتعامل باستمرار مع بيانات قد تكون ناقصة، وكائنات معقدة، وواجهات Java قديمة، وتغيّرات في الحالة.

إذا اعتمدت على فحص هذه الحالات يدويًا في كل مكان، ستظهر مشكلات مثل:

  • تكرار null checks.
  • أخطاء ناتجة عن افتراضات غير صحيحة حول أنواع البيانات.
  • زيادة الكود الذي لا يضيف قيمة وظيفية.
  • صعوبة معرفة نوع القيمة التي تعيدها دالة أو تستقبلها.

Kotlin تعالج هذه المشكلات من خلال مجموعة خصائص متكاملة: concise syntax وnull safety وinteroperability وtype inference.

2.2 كيف تعمل (How It Works)

أولًا: Concise Syntax

Kotlin توفر syntax يقلل الكود المتكرر ويجعل بعض الأفكار البرمجية أكثر مباشرة.

مثلًا، Java تحتاج عادةً إلى كتابة تعريف class وconstructor وحقول وعمليات متعلقة بها.

في Kotlin:

data class Customer(
    val id: Long,
    val name: String,
    val phone: String?
)

التعريف السابق يصف البيانات التي يحتاجها التطبيق، بينما يتولى compiler إنشاء عدد من العمليات المعتادة المرتبطة بها.

ومن أمثلة الاختصار أيضًا:

تعريف المتغيرات

  • val: تعريف reference لا يمكن إعادة إسناده.
  • var: تعريف متغير يمكن إعادة إسناده.
val transactionId = "TX-901"
var retryCount = 0

retryCount++

هناك تفصيلة مهمة: val لا يضمن immutability للكائن نفسه.

val names = mutableListOf("Ahmed", "Mona")

names.add("Ali") // Allowed

لا يمكن استبدال reference الخاص بـ names، لكن يمكن تعديل القائمة نفسها.

Functions

يمكن تعريف function مباشرة دون إنشاء class يحتوي عليها:

fun calculateTotal(
    amount: Long,
    fee: Long
): Long {
    return amount + fee
}

كذلك يمكن استخدام expression body:

fun calculateTotal(amount: Long, fee: Long): Long =
    amount + fee

الاختصار هنا يزيل البنية الشكلية غير الضرورية، لكنه لا يغيّر الغرض من الدالة.

ثانيًا: Null Safety

Null safety هي ميزة في Kotlin تجعل إمكانية احتواء المتغير على null جزءًا صريحًا من type system، وتتيح للـ compiler التحقق من كثير من حالات استخدامها غير الآمن.

هذه من أهم خصائص Kotlin.

في Kotlin يوجد فرق بين:

val name: String = "Ahmed"
val phone: String? = null

النوع String لا يقبل null، بينما String? يقبلها.

وجود ? في النوع ليس مجرد annotation؛ بل يغيّر العمليات المسموح بها على القيمة.

مثلًا:

val length = phone.length

هذا غير مقبول؛ لأن phone قد تكون null.

يمكن استخدام safe-call operator، وهو العامل ?. الذي ينفّذ الوصول إلى الخاصية أو الدالة فقط عندما تكون القيمة غير null:

val length = phone?.length

إذا كانت phone تساوي null، تكون النتيجة null بدلًا من محاولة الوصول إلى الخاصية.

ويمكن استخدام Elvis operator، وهو ?: الذي يوفر قيمة بديلة عندما تكون النتيجة null:

val displayedPhone = phone ?: "غير متاح"

يمكن الجمع بينهما:

val displayedLength = phone?.length ?: 0

ماذا يفعل compiler؟

عندما يكتشف أن المتغير من نوع String، يسمح باستخدام خصائصه مباشرة.

أما إذا كان من نوع String?، فيطلب منك التعامل مع احتمال عدم وجود القيمة.

على سبيل المثال:

fun displayName(name: String?) {
    if (name != null) {
        println(name.length)
    }
}

داخل الشرط، يستطيع compiler معرفة أن name غير null، فيسمح باستخدامه كـ String.

هذا السلوك يسمى smart cast: قدرة Kotlin compiler على استخدام النوع الأكثر تحديدًا بعد التحقق من شروط معينة على القيمة.

لكن smart cast لا يمكن تطبيقه في كل الظروف؛ فقد يتعذر على compiler ضمان استقرار القيمة، مثل بعض حالات mutable properties أو الخصائص التي يمكن أن تتغير من مكان آخر.

حدود Null Safety

لا تعني Null Safety استحالة حدوث NullPointerException.

هناك حالات يمكن أن تفشل فيها، أهمها:

  • استخدام !!، وهو operator يطلب من compiler التعامل مع القيمة على أنها غير null، مع رمي NullPointerException إذا كانت null.
  • استدعاء كود Java يعيد قيمة غير موصوفة بوضوح من ناحية nullability.
  • وجود أخطاء في initialization أو تسريب this قبل اكتمال تهيئة الكائن.
  • تجاوز type contracts عبر Java أو بعض الاستخدامات غير الآمنة للـ generics.

إذًا Null Safety تقلل مساحة الأخطاء، لكنها لا تلغي مسؤولية تصميم العقود بين أجزاء النظام.

ثالثًا: Interoperability

Interoperability تعني قدرة Kotlin على التكامل مع لغات ومنصات أخرى، وخاصة Java داخل JVM ecosystem.

في Android، هذه القدرة أساسية؛ لأن Android SDK ومكتبات كثيرة ومشروعات قائمة تحتوي على Java code.

يمكنك استدعاء Java class من Kotlin:

val formatter = java.text.SimpleDateFormat(
    "yyyy-MM-dd",
    java.util.Locale.US
)

val formattedDate = formatter.format(date)

ويمكن استدعاء Kotlin code من Java أيضًا.

لكن التكامل لا يعني أن اللغتين لهما type systems متطابقة.

أهم مثال هو nullability.

عندما يستقبل Kotlin قيمة من Java لا تحتوي على nullability annotations مفهومة، فقد يعاملها compiler باعتبارها platform type.

الـ platform type هو نوع قادم من Java لا يستطيع Kotlin تحديد ما إذا كان يقبل null بصورة مؤكدة أم لا.

قد ترى هذا الرمز في رسائل compiler أو IDE:

String!

ومعناه أن النوع قد يتصرف كـ String أو String? حسب القيمة الفعلية.

لذلك قد يقبل الكود التالي compilation:

val name: String = javaUser.getName()

لكن إذا أعادت Java القيمة null، فقد يحدث فشل أثناء التشغيل.

الأفضل أن تحدد عقد nullability صراحةً عند الحدود بين Java وKotlin:

val name: String? = javaUser.getName()

ثم تتعامل مع احتمال غياب القيمة.

دعم nullability annotations يساعد على تحسين هذا التكامل، ومن أمثلته @Nullable و@NotNull وJSpecify annotations.

رابعًا: Type Inference

Type inference هي قدرة compiler على استنتاج نوع المتغير أو التعبير من السياق دون الحاجة إلى كتابته يدويًا.

مثلًا:

val amount = 1500L

يستنتج compiler أن amount من النوع Long.

وكذلك:

val customerName = "Ahmed"

يستنتج أن النوع String.

المهم أن الاستنتاج يحدث أثناء compilation، وليس أثناء تشغيل التطبيق.

أي أن Kotlin تظل statically typed language.

قارن:

val balance = 2500L

النوع معروف بالفعل عند compilation.

val balance: Long = 2500L

التصريح بالنوع صراحةً هنا يعطي النتيجة نفسها.

يمكن للـ compiler أيضًا استنتاج أنواع expressions من السياق:

val customer = loadCustomer()

fun loadCustomer(): Customer {
    // Load customer from repository
    TODO()
}

في هذا المثال نوع customer معلوم لأنه مستنتج من return type للدالة.

لكن type inference لا يعمل عندما لا توجد معلومات كافية لاستنتاج النوع.

والأهم أن إخفاء النوع ليس دائمًا مفيدًا. في public APIs، التصريح الواضح عن parameter types وreturn types يجعل العقد أكثر وضوحًا ويساعد على فهم الكود وصيانته.

2.3 مثال واقعي (Real-world Example)

لنفترض أنك تطور شاشة تفاصيل مستفيد في تطبيق تحويلات مالية.

قد يأتي اسم المستفيد ورقم الهاتف من backend، وليس مضمونًا أن تتوفر كل البيانات.

يمكن كتابة:

data class Beneficiary(
    val id: Long,
    val name: String?,
    val phone: String?
)

fun getDisplayName(beneficiary: Beneficiary): String =
    beneficiary.name ?: "مستفيد غير معروف"

هنا استفدت من:

  • Concise syntax لتقليل الكود الخاص بتمثيل البيانات.
  • Null safety للتعبير عن أن الاسم قد لا يكون موجودًا.
  • Type inference لاستنتاج نوع المتغيرات المحلية عند معرفة قيمها.
  • Interoperability لإمكانية استهلاك كائنات ومكتبات Java عند الحاجة.

لكن انتبه إلى الفرق بين صحة النوع وصحة البيانات.

كون amount من النوع Long لا يضمن أنه يمثل مبلغًا ماليًا صحيحًا، ولا يضمن أنه موجب أو متوافق مع العملة.

يمكن للـ type system أن يضمن بعض القيود، أما business validation فيحتاج إلى منطق مستقل.

2.4 البدائل (Alternatives)

عند التعامل مع هذه الخصائص، هناك اختيارات تصميمية مهمة:

التصريح بالنوع مقابل Type Inference

استخدم inference للمتغيرات المحلية عندما يكون النوع واضحًا من السياق، واكتب النوع صراحةً عندما يكون ذلك مفيدًا لفهم public API أو إزالة الالتباس.

Null مقابل أنواع بديلة

استخدم nullable types عندما يكون غياب القيمة جزءًا حقيقيًا من العقد.

أما عندما تحتاج إلى التعبير عن نتيجة تحتوي على نجاح أو فشل أو تفاصيل إضافية، فقد يكون model صريح مثل Result أو sealed hierarchy أفضل من مجرد null.

الاعتماد على Java مقابل كتابة Kotlin wrappers

يمكنك استخدام Java APIs مباشرة، أو إنشاء Kotlin wrapper يحدد العقود بشكل أوضح.

الخيار الثاني مفيد عندما تتكرر مشكلة nullability أو وجود API قديمة تحتاج إلى عزلها عن بقية طبقات التطبيق.

2.5 أين يفشل (Failure Modes)

أكثر الأخطاء أهمية هو الاعتقاد بأن String? يحل جميع مشكلات null.

قد تستقبل قيمة من Java كـ platform type، فتسمح Kotlin بتمريرها إلى مكان يتوقع قيمة non-null، ثم تفشل أثناء runtime.

مثال آخر هو استخدام !! لإسكات compiler:

val accountName = response.account!!.name!!

هذا يحول مشكلة واضحة أثناء compilation إلى احتمال حدوث crash أثناء التشغيل.

أعراض المشكلة:

  • NullPointerException رغم استخدام Kotlin.
  • ظهور مشاكل null في أجزاء تتعامل مع Java.
  • اعتماد عدد كبير من أجزاء التطبيق على !!.
  • كود لا يحتاج إلى null checks رغم أن البيانات الخارجية غير مضمونة.

التشخيص:

ابدأ عند الحدود الخارجية: Java APIs، وnetwork responses، وdatabase results، والبيانات التي تأتي من Android framework.

تحقق من أنواع القيم الفعلية، ومن nullability annotations، ولا تفترض أن compiler يستطيع استنتاج ضمانات لم تقدمها له الواجهات الخارجية.

2.6 قاعدة القرار (Decision Rule)

اجعل nullability صريحة في العقود، واستفد من type inference عندما يكون النوع واضحًا، واستخدم concise syntax لتقليل التكرار دون التضحية بالوضوح.

أما عند التعامل مع Java أو البيانات الخارجية، فتعامل مع القيم على أنها غير موثوقة حتى تحدد nullability الفعلية لها.

3. Where Kotlin Runs

3.1 المشكلة (Problem)

من الأخطاء الشائعة ربط Kotlin بـ Android فقط.

لكن Kotlin صُممت لتعمل في بيئات متعددة.

المشكلة التي تحاول هذه الإمكانية حلها هي أن فرق التطوير غالبًا تحتاج إلى مشاركة منطق الأعمال بين تطبيقات ومكونات تعمل على منصات مختلفة.

مثلًا، شركة لديها:

  • Android application.
  • iOS application.
  • Backend services.
  • Web application.

قد تحتاج هذه الأنظمة إلى تطبيق قواعد مشتركة، مثل validation وحساب الأسعار وتحليل البيانات.

إعادة كتابة المنطق نفسه في عدة لغات تزيد احتمالات اختلاف السلوك، كما تزيد تكلفة الصيانة.

لكن تشغيل اللغة على منصات مختلفة يفرض قيودًا تقنية؛ فكل منصة لها runtime وواجهات نظام ومكتبات مختلفة.

3.2 كيف تعمل (How It Works)

Mental Model

Kotlin لغة واحدة، لكن لديها أكثر من compilation target.

Compilation target هو المنصة أو بيئة التنفيذ التي ينتج compiler كودًا متوافقًا معها.

لا تفترض أن كل Kotlin code يتحول إلى نفس نوع الملفات أو يعمل على نفس runtime.

المسارات الرئيسية هي:

1. Kotlin/JVM

JVM هي اختصار Java Virtual Machine، وهي بيئة تشغيل تنفذ JVM bytecode وتوفر خدمات مثل إدارة الذاكرة.

عند استخدام Kotlin/JVM، يقوم compiler بتحويل ملفات Kotlin إلى Java class files تحتوي على JVM bytecode.

يمكن تشغيل هذه الملفات على JVM، سواء في تطبيق backend أو desktop application.

2. Kotlin on Android

Android تستخدم جزءًا من نفس منظومة Java bytecode، لكنها لا تشغل تطبيقات Android بالطريقة التقليدية نفسها التي تشغل بها Java applications على JVM desktop.

DEX هو تنسيق bytecode مخصص لـ Android، مصمم ليتناسب مع بيئة التشغيل على الأجهزة المحمولة.

D8 أداة تحول JVM class files إلى DEX، بينما يستطيع R8 تنفيذ shrinking وoptimization وإنتاج DEX أيضًا.

ART، أو Android Runtime، هي بيئة تشغيل تطبيقات Android التي تنفذ DEX وتستفيد من تقنيات مثل JIT وAOT compilation.

إذًا عندما تكتب Kotlin في تطبيق Android، لا توجد Kotlin VM مستقلة على الجهاز. تنتقل مخرجات Kotlin إلى Android build toolchain، ثم يعمل التطبيق ضمن Android Runtime.

هذا المسار مهم لفهم أن Kotlin وJava يمكن أن يتعايشا داخل التطبيق نفسه، وأن كليهما يمر عبر منظومة التنفيذ الخاصة بـ Android.

3. Server-side Kotlin

يمكن استخدام Kotlin في تطوير Backend applications.

في هذا السيناريو، غالبًا تستهدف JVM وتستفيد من مكتبات Java وframeworks الموجودة.

من الأمثلة:

  • Spring Boot.
  • Ktor.
  • Vert.x.

بالتالي يستطيع فريق Android مشاركة بعض الأفكار أو حتى بعض المكتبات مع فريق backend، دون الحاجة إلى استخدام لغة مختلفة تمامًا.

تدعم Kotlin التكامل مع Java frameworks، مما يسمح بتبنيها تدريجيًا داخل مشروعات Java server-side.

4. Kotlin/JS and Kotlin/Wasm

يمكن أن تستهدف Kotlin بيئة JavaScript، بحيث يُترجم الكود إلى JavaScript يمكن تشغيله في بيئات تدعمه.

كما يوجد Kotlin/Wasm، الذي يتيح إنتاج WebAssembly code.

WebAssembly هو تنسيق تنفيذي منخفض المستوى يمكن تشغيله في بيئات تدعم WebAssembly، ومنها متصفحات الويب.

الفكرة هنا أن منطقًا مكتوبًا بـ Kotlin يمكن أن يعمل خارج JVM تمامًا.

5. Kotlin/Native

Kotlin/Native هو compiler backend يحول Kotlin إلى native binaries بدلًا من إنتاج JVM bytecode.

يتيح هذا استخدام Kotlin على منصات مثل iOS، حيث لا تعتمد بيئة التطبيق على JVM.

وهنا يظهر فرق مهم: Kotlin/Native ليست Kotlin/JVM تعمل بطريقة مختلفة قليلًا؛ إنها تستهدف runtime وبيئة تنفيذ مختلفتين.

6. Kotlin Multiplatform (KMP)

Kotlin Multiplatform هي تقنية تسمح بمشاركة الكود بين منصات مختلفة، مع الاحتفاظ بإمكانية كتابة أجزاء خاصة بكل منصة.

قد تشارك:

  • Business logic.
  • Networking.
  • Data models.
  • Validation rules.
  • بعض مكونات UI عند استخدام Compose Multiplatform.

ليس من الضروري أن تشارك كل التطبيق.

يمكن أن يكون لديك Android UI مكتوب بـ Jetpack Compose، وiOS UI مكتوب بـ SwiftUI، مع مشاركة طبقة business logic بينهما.

وهذه من أهم أفكار KMP: مشاركة الكود تدريجيًا حسب ما يناسب بنية النظام، لا فرض واجهة أو architecture واحدة على جميع المنصات.

3.3 مثال واقعي (Real-world Example)

لنفترض أن لديك نظام تجارة إلكترونية يتكون من Android وiOS وBackend.

توجد قاعدة لحساب أهلية العميل للحصول على خصم:

data class Order(
    val totalMinor: Long,
    val completedOrders: Int
)

fun isEligibleForDiscount(order: Order): Boolean =
    order.totalMinor >= 10_000 &&
        order.completedOrders >= 3

يمكن أن يكون هذا المنطق جزءًا من shared Kotlin module.

يستهلكه تطبيق Android، ويستهلكه تطبيق iOS، ويمكن أن يستفيد منه مكون Backend أيضًا.

لكن تختلف طريقة الوصول إلى APIs الخاصة بكل منصة.

مثلًا، الوصول إلى Android-specific APIs أو iOS-specific APIs لا يصبح تلقائيًا مشتركًا لمجرد أن الكود مكتوب بـ Kotlin.

تحتاج إلى فصل الأجزاء المشتركة عن الأجزاء المرتبطة بالمنصة.

3.4 البدائل (Alternatives)

عند التفكير في مشاركة الكود بين المنصات، توجد عدة خيارات:

Native implementation لكل منصة: تكتب Android بـ Kotlin/iOS بـ Swift، وتكرر المنطق المشترك في كل تطبيق. يمنحك استقلالية كاملة، لكنه يرفع تكلفة صيانة المنطق المكرر.

Kotlin Multiplatform: تشارك أجزاء من المنطق المكتوب بـ Kotlin، مع السماح لكل منصة باستخدام APIs الخاصة بها. مناسب عندما تكون مشاركة business logic أهم من توحيد واجهة المستخدم.

Cross-platform UI frameworks: مثل Flutter أو React Native، حيث يكون التركيز على مشاركة قدر أكبر من واجهة المستخدم وتجربة التطبيق. تختلف المقايضات المتعلقة باللغة والأدوات والتكامل مع المنصة.

هذه البدائل ليست متطابقة في أهدافها؛ فلا تختَر تقنية لمجرد أنها cross-platform، بل حدد أولًا ما الذي تريد مشاركته.

3.5 أين يفشل (Failure Modes)

أحد الأخطاء الشائعة هو افتراض أن أي Kotlin library يمكن استخدامها على iOS لأنها مكتوبة بـ Kotlin.

هذا غير صحيح؛ فقد تعتمد المكتبة على JVM APIs أو Android SDK، وهي غير متاحة بالضرورة في Kotlin/Native.

كذلك قد يكون الكود صالحًا داخل commonMain من منظور اللغة، لكنه يعتمد على مكتبة غير مدعومة في أحد targets.

ومن الأخطاء الأخرى مشاركة كل شيء دون دراسة تكلفة ذلك.

مثلًا، قد يكون من الأفضل إبقاء واجهة المستخدم native لكل منصة، بدلًا من محاولة توحيد واجهة تختلف فيها متطلبات الوصول والتفاعل والتصميم.

الأعراض:

  • نجاح compilation على Android وفشله على iOS.
  • اعتماد shared module على platform-specific APIs.
  • صعوبة دمج المكتبات بين targets.
  • مشاركة واجهات المستخدم بشكل يجعل تطوير كل منصة أكثر تعقيدًا.

التشخيص: حدد target لكل module، وافحص المكتبات التي يعتمد عليها، وافصل common code عن platform-specific code.

3.6 قاعدة القرار (Decision Rule)

استخدم Kotlin/JVM عندما يكون هدفك Android أو JVM backend.

استخدم KMP عندما توجد أجزاء حقيقية من منطق النظام تستحق المشاركة بين منصات متعددة، بشرط التأكد من توافق dependencies والـ targets.

لا تجعل مشاركة الكود هدفًا بحد ذاتها؛ الهدف هو تقليل التعقيد والتكرار دون فرض قيود أكبر على النظام.

4. Kotlin and Java Compared

4.1 المشكلة (Problem)

في مشروعات Android الواقعية، ستجد Kotlin وJava في المشروع نفسه.

قد يكون لديك مشروع بدأ قبل سنوات باستخدام Java، ثم أضيفت إليه features جديدة باستخدام Kotlin.

وقد تعتمد على libraries مكتوبة بـ Java، بينما تكتب أنت business logic باستخدام Kotlin.

لذلك، السؤال الهندسي ليس: أي اللغتين أفضل؟

السؤال هو: كيف تتعايش اللغتان؟ وما حدود التوافق بينهما؟ وما الذي يتغير عند كتابة الكود بإحداهما؟

4.2 كيف تعمل (How It Works)

أولًا: Syntax

أحد الفروق الواضحة هو مقدار الكود اللازم للتعبير عن الفكرة.

لنفترض أنك تريد الحصول على اسم العميل، مع توفير قيمة بديلة إذا لم يكن الاسم موجودًا.

في Java:

public String getDisplayName(User user) {
    String name = user.getName();

    if (name == null) {
        return "Unknown";
    }

    return name;
}

في Kotlin:

fun getDisplayName(user: User): String =
    user.name ?: "Unknown"

الفرق ليس في الوظيفة النهائية، بل في مقدار البنية التي تحتاج إلى كتابتها.

من أهم الفروق في syntax:

  • Kotlin تستخدم val وvar بدلًا من التصريح التقليدي بالمتغيرات مع modifiers منفصلة.
  • Kotlin لديها properties، بينما Java تعتمد عادةً على fields وgetter/setter methods.
  • Kotlin توفر primary constructors لتقليل الكود المتعلق بتهيئة الكائنات.
  • Kotlin توفر default arguments وnamed arguments.
  • Kotlin لديها nullability مدمجة في type system.
  • Kotlin تسمح بتعريف functions خارج classes.

هذه الاختلافات تجعل Kotlin أكثر تعبيرًا في كثير من السيناريوهات اليومية.

ثانيًا: Interoperability

Kotlin calls Java

يمكن لـ Kotlin استدعاء Java classes وmethods مباشرة، بما فيها المكتبات الموجودة مسبقًا.

كما تستطيع Kotlin استخدام Java collections وJava APIs.

Java calls Kotlin

يمكن لـ Java استدعاء Kotlin functions وclasses التي ينتج عنها JVM bytecode متوافق.

لكن بعض Kotlin constructs تحتاج إلى مراعاة عند تصميم public APIs.

على سبيل المثال، Kotlin تدعم default arguments:

fun generateReport(format: String = "pdf") {
    // Generate report
}

يمكن استدعاء الدالة من Kotlin دون تمرير قيمة:

generateReport()

لكن Java لا تتعامل مع Kotlin default arguments بالطريقة نفسها تلقائيًا.

يمكن استخدام @JvmOverloads، وهي annotation تجعل compiler يولّد Java overloads لبعض الدوال التي تحتوي على default parameters:

@JvmOverloads
fun generateReport(format: String = "pdf") {
    // Generate report
}

بهذا يمكن لشفرة Java استدعاء overload دون تمرير كل المعاملات الاختيارية.

ومن الخصائص الأخرى التي يجب الانتباه إليها عند تصميم APIs:

  • Kotlin properties تظهر غالبًا في Java من خلال getter/setter methods.
  • Kotlin top-level functions تُترجم إلى methods في class مولد.
  • Kotlin internal لا تعني أن Java لن تتمكن من رؤية الرمز الناتج على مستوى bytecode.
  • @JvmStatic يمكن استخدامها لتوليد static method مناسبة لاستهلاك Java في بعض الحالات.

الهدف هو عدم تصميم API بمعزل عن اللغة التي ستستهلكها.

ثالثًا: Runtime

هذه أهم نقطة في المقارنة.

لا يوجد Java runtime منفصل وKotlin runtime منفصل داخل Android application.

عند استهداف JVM:

وبالتالي يمكن أن تتفاعل Java class مع Kotlin class داخل التطبيق نفسه.

هناك فرق متعلق بـ Kotlin standard library.

بعض وظائف Kotlin تعتمد على مكتباتها القياسية، ولذلك يحتاج التطبيق إلى توفير الاعتماديات المناسبة.

لكن هذا لا يعني وجود runtime مستقل لتشغيل لغة Kotlin على Android.

من المهم أيضًا ألا تخلط بين اللغة والأداء.

كتابة function في Kotlin بدلًا من Java لا تعني تلقائيًا أنها ستعمل أسرع أو أبطأ. الأداء يعتمد على الكود الناتج، والـ runtime، وطريقة الاستخدام، وعمليات optimization.

4.3 مثال واقعي (Real-world Example)

لنفترض أنك تعمل على تطبيق مصرفي كبير، يحتوي على Java modules مسؤولة عن إدارة الحسابات والمعاملات.

تريد إضافة feature جديدة لإظهار سجل التحويلات باستخدام Kotlin.

ليس من الضروري إعادة كتابة طبقة الحسابات القديمة.

يمكنك استهلاك Java service مباشرة:

class TransferRepository(
    private val legacyService: LegacyTransferService
) {
    fun loadTransfers(): List<Transfer> {
        return legacyService.getTransfers()
    }
}

وتستطيع LegacyTransferService نفسها أن تكون مكتوبة بالكامل بـ Java.

القرار الهندسي هنا هو الحفاظ على الأجزاء المستقرة، وإدخال Kotlin في الأماكن التي تحقق فيها قيمة واضحة.

عند التعامل مع Java methods التي لا توضح nullability، يجب تحديد العقد في طبقة التكامل بدلًا من نشر platform types في كل طبقات التطبيق.

مثلًا:

fun getCustomerName(user: LegacyUser): String? {
    return user.getName()
}

بهذه الطريقة، تصبح Kotlin مسؤولة عن توضيح العقد الذي لم يكن محددًا بشكل كافٍ في Java API.

4.4 البدائل (Alternatives)

يمكنك الاستمرار في Java، أو اعتماد Kotlin في الكود الجديد، أو تنفيذ migration تدريجي إلى Kotlin.

الاستمرار في Java مناسب عندما يكون المشروع مستقرًا ولا توجد فائدة كافية لتغيير اللغة.

أما استخدام اللغتين معًا فيناسب المشروعات الكبيرة؛ إذ يسمح بتحسين الأجزاء الجديدة دون المخاطرة بإعادة كتابة واسعة.

الهجرة الكاملة إلى Kotlin قد تكون مناسبة عندما توجد أسباب تقنية وتنظيمية قوية، لكنها ليست شرطًا للاستفادة من اللغة.

4.5 أين يفشل (Failure Modes)

المشكلة الأولى: افتراض أن Null Safety تنتقل تلقائيًا إلى Java

إذا كتبت:

fun findAccount(id: Long): Account?

فهذا يعبّر بوضوح عن nullability في Kotlin، لكن Java لا تفرض دائمًا العقد نفسه عند compilation بالطريقة التي يفعلها Kotlin compiler.

يجب الاهتمام بالـ annotations وعقد الـ API عند عبور الحدود بين اللغتين.

المشكلة الثانية: افتراض أن Kotlin syntax كلها متاحة بالطريقة نفسها في Java

مثلًا، Java لا تستطيع استخدام default arguments مباشرة، وبعض Kotlin language features تحتاج إلى bytecode representation مناسب عند استهلاكها من Java.

المشكلة الثالثة: تسريب platform types

عندما تعتمد طبقات التطبيق على قيم Java غير محددة nullability، قد تنتشر حالات عدم اليقين في كل مكان.

أعراض المشكلات:

  • NullPointerException في كود Kotlin رغم استخدام nullable types.
  • عدم قدرة Java code على استدعاء API كما هو متوقع.
  • ظهور overloads غير مناسبة.
  • صعوبة تغيير implementation دون التأثير في المستهلكين.

التشخيص: افحص الـ generated API والـ bytecode عند الحاجة، وراجع Java signatures وnullability annotations، واختبر التكامل من جانبي اللغة.

4.6 قاعدة القرار (Decision Rule)

عامل Java وKotlin على أنهما لغتان متكاملتان ضمن بيئة JVM، وليس نظامين منفصلين.

عند تطوير Kotlin code يستهلكه Java، صمم public APIs مع مراعاة طريقة ظهورها في Java.

وعند استهلاك Java code من Kotlin، لا تفترض null safety إلا عندما يكون عقد nullability واضحًا.

5. Kotlin Versions and the K2 Compiler

5.1 المشكلة (Problem)

لغة البرمجة ليست شيئًا ثابتًا؛ تتطور بمرور الوقت.

تُضاف ميزات جديدة، وتتحسن diagnostics، ويتغير compiler، وقد تتغير طريقة تفسير بعض الحالات الحدّية في الكود.

في مشروع Android، لا تستطيع تحديث Kotlin بمعزل عن بقية أدوات البناء دائمًا.

توجد علاقة بين:

  • Kotlin compiler.
  • Kotlin Gradle Plugin.
  • Android Gradle Plugin (AGP).
  • Gradle.
  • JDK.
  • D8 وR8.
  • أدوات وplugins أخرى مثل Compose compiler plugin.

إذا كانت الإصدارات غير متوافقة، قد يفشل compilation أو يحدث اختلاف في سلوك أدوات البناء.

لذلك يحتاج مهندس Android إلى فهم معنى الإصدار، وليس مجرد اختيار أحدث رقم متاح.

5.2 كيف تعمل (How It Works)

أولًا: Kotlin Versions

Kotlin تستخدم نظام إصدارات من الشكل:

Major.Minor.Patch

مثل:

2.4.21

توضح الأجزاء بصورة عامة:

  • Major: إصدار رئيسي يتضمن تطورات كبيرة.
  • Minor: إصدار يتضمن تطورات وميزات جديدة.
  • Patch: تحديثات إصلاح وتحسين للإصدار الأساسي.

هذا تقسيم عملي لفهم أرقام الإصدارات، وليس بديلًا عن مراجعة release notes؛ فقد تختلف طبيعة التغييرات بين الإصدارات.

ما أحدث إصدار؟

اعتبارًا من 19 نوفمبر 2026، أحدث إصدار stable موثق في صفحة Kotlin الرسمية هو:

Latest stable Kotlin 2.4.21

صدر في 8 أكتوبر 2026، وهو إصدار bug fixes ضمن سلسلة Kotlin 2.4.

تستطيع مراجعة الإصدارات والتغييرات عبر:

ثانيًا: لا تخلط بين أنواع الإصدارات

هذه نقطة مهمة جدًا في Android.

عندما ترى رقمًا مثل 2.4.21 في Gradle configuration، فقد يكون المقصود إصدار Kotlin Gradle Plugin الذي يحدد نسخة compiler المستخدمة في بناء المشروع.

لكن هناك إعدادات أخرى مستقلة:

Compiler Version

إصدار compiler نفسه والأدوات المرتبطة به.

Language Version

يحدد إصدار قواعد اللغة والميزات التي يسمح compiler باستخدامها.

API Version

يحدد مستوى Kotlin standard library API الذي يسمح الكود باستخدامه.

JVM Target

يحدد مستوى JVM bytecode المستهدف عند compilation.

وهنا خطأ شائع:

JVM Target ليس هو minSdk في Android.

الأول يتعلق بصيغة bytecode الناتجة، أما الثاني فيحدد أقل إصدار Android يستهدفه التطبيق من ناحية platform APIs.

اختلافهما يعني أن رفع JVM Target لا يرفع تلقائيًا minSdk، والعكس صحيح.

ثالثًا: K2 Compiler

K2 هو الجيل الجديد من Kotlin compiler، ويقدم architecture أحدث لتحليل الكود والتحقق من الأنواع وإجراء compilation.

قبل K2، كان Kotlin يستخدم compiler implementation أقدم.

بدأ تطوير K2 لمعالجة تحديات الأداء وقابلية التوسع وتوحيد البنية الداخلية للـ compiler عبر منصات Kotlin المختلفة.

في Kotlin 2.0.0 أصبح K2 stable ومفعّلًا افتراضيًا لجميع targets الرئيسية التي تدعمها اللغة، ومنها JVM وNative وJS وWasm.

ما الذي يقدمه K2؟

هناك عدة تحسينات مهمة:

  1. تحسين أداء compilation في كثير من المشروعات.
  2. تحسين استقرار وسرعة code analysis في IDE.
  3. بنية موحدة بشكل أفضل عبر منصات Kotlin.
  4. تسهيل تطوير ميزات اللغة الجديدة.
  5. تحسينات في تحليل الكود وتشخيص بعض الأخطاء.

لكن يجب فهم نقطة مهمة:

K2 هو compiler، وليس runtime جديدًا.

لا يعني الانتقال إلى K2 أن تطبيق Android سيعمل على بيئة تنفيذ مختلفة عن ART.

كما أنه لا يغيّر المبدأ الأساسي الذي يجعل Java وKotlin تتعايشان داخل التطبيق نفسه.

رابعًا: أين يعمل K2؟

يمكن تقسيم عمل compiler إلى مرحلتين من ناحية فهم المسؤوليات:

Build Time

هنا يقوم K2 بتحليل Kotlin source code والتحقق منه وإنتاج المخرجات المناسبة.

هذا يحدث على جهاز المطور أو داخل CI environment.

Application Runtime

بعد انتهاء compilation، تعمل المخرجات ضمن البيئة المستهدفة، مثل ART على Android.

K2 لا يراقب كل function أثناء تنفيذ التطبيق، ولا يحل محل ART.

منذ Kotlin 2.0 أصبح K2 هو compiler الافتراضي. ومن Kotlin 2.4 لم يعد الرجوع إلى compiler القديم خيارًا مدعومًا بالطريقة التي كانت متاحة في بعض الإصدارات السابقة.

5.3 مثال واقعي (Real-world Example)

لنفترض أن لديك تطبيق Android يعمل بـ Kotlin 2.1، وتريد تحديثه إلى Kotlin 2.4.21.

قد يبدو التغيير بسيطًا:

Kotlin 2.1.x
      |
      v
Kotlin 2.4.21

لكن تحديث compiler فقط قد لا يكون كافيًا.

يجب التحقق من توافق Android Gradle Plugin وD8/R8 وبقية أدوات البناء.

مثلًا، توضح صفحة Android الرسمية الخاصة بتوافق AGP وD8 وR8 أن Kotlin 2.4 يحتاج إلى AGP 8.5.2 أو أحدث، مع متطلبات محددة لـ R8. كما أن AGP يضم D8 وR8 ضمن حزمة الأدوات الخاصة به.

إذًا، قبل ترقية المشروع، لا تنظر إلى رقم Kotlin وحده.

افحص مصفوفة التوافق، ثم نفّذ build واختبارات المشروع باستخدام toolchain المتوافقة.

يمكنك الوصول إلى المرجع الرسمي هنا:

AGP, D8, and R8 versions required for Kotlin versions.

5.4 البدائل (Alternatives)

عند اختيار إصدار Kotlin، توجد ثلاثة اتجاهات:

Latest Stable

مناسب للمشروعات التي تستطيع تحديث toolchain والتحقق من توافق dependencies.

ميزته الحصول على إصلاحات compiler والميزات الجديدة، لكن تكلفة التحديث قد تشمل تعديل build configuration أو معالجة تغييرات في diagnostics.

إصدار أقدم ومستقر داخل المشروع

مناسب عندما تكون هناك قيود تتعلق بـ AGP أو Gradle أو مكتبات خارجية.

ليس المطلوب أن تستخدم أحدث نسخة في كل مشروع، بل أن تستخدم نسخة مدعومة ومتوافقة مع بقية الأدوات.

Early Access Preview (EAP)

نسخ تجريبية تتيح تجربة الميزات قبل وصولها إلى stable release.

تكون مفيدة عند تقييم تغييرات مستقبلية أو اختبار توافق مكتبة، لكنها ليست الاختيار المعتاد لنسخة production دون سبب واضح.

5.5 أين يفشل (Failure Modes)

المشكلة الأولى: تحديث Kotlin دون تحديث toolchain

قد يحدث compilation failure بسبب عدم توافق Kotlin Gradle Plugin مع AGP أو بقية الأدوات.

التشخيص: راجع Android compatibility requirements الخاصة بإصدار Kotlin المستخدم، وليس فقط release notes الخاصة باللغة.

المشكلة الثانية: الخلط بين K2 وART

قد يعتقد المطور أن تفعيل K2 يغيّر طريقة تشغيل التطبيق على Android.

هذا غير صحيح.

K2 مسؤول عن compilation، بينما ART مسؤولة عن execution.

التشخيص: حدد هل المشكلة تظهر أثناء build أم أثناء runtime.

إذا فشل compiler في تحليل الكود، فالمشكلة في build pipeline. وإذا انهار التطبيق بعد تثبيته، فابحث في runtime behavior.

المشكلة الثالثة: اعتبار كل تغيير في diagnostics خطأ جديدًا في التطبيق

عند الانتقال إلى K2، قد تلاحظ اختلافًا في diagnostics أو قواعد التحليل لبعض الحالات.

هذا لا يعني بالضرورة أن runtime تغير.

راجع سبب الرسالة، ثم أصلح الكود وفق contract واضح بدلًا من محاولة إسكات compiler.

المشكلة الرابعة: الخلط بين Kotlin version وJDK version

Kotlin compiler يستهدف JVM bytecode، ويحتاج إلى بيئة وأدوات Java مناسبة أثناء build، لكن إصدار Kotlin ليس هو إصدار JDK.

يمكن أن تواجه build failure إذا لم تتوافق متطلبات الأدوات، حتى عندما يكون كود Kotlin نفسه صحيحًا.

المشكلة الخامسة: افتراض أن أحدث إصدار هو الأفضل دائمًا

قد تكون لديك dependencies لا تدعم النسخة الجديدة، أو build infrastructure لا تتوافق معها بعد.

الترقية ليست مجرد تغيير رقم؛ إنها تغيير في جزء من toolchain الإنتاجية.

5.6 قاعدة القرار (Decision Rule)

اختر أحدث إصدار stable عندما تكون بقية أدوات المشروع متوافقة معه، ولا تستخدم EAP في production إلا لسبب مدروس.

عند تحديث Kotlin، تحقق من Kotlin Gradle Plugin وAGP وGradle وJDK وD8/R8، وافصل بين أخطاء compilation وأخطاء runtime.

وتذكّر أن K2 هو compiler architecture حديث، وليس runtime بديلًا عن ART.

هذا الرسم يوضح مسارًا أساسيًا، وليس كل تفاصيل compilation الخاصة بكل target.

هناك خمس أفكار ينبغي الاحتفاظ بها:

  1. Kotlin لغة statically typed، وليست مجرد Java syntax مختلفة.
  2. Null safety ميزة في type system، لكنها لا تحمي تلقائيًا الحدود غير الموثوقة، خصوصًا عند التعامل مع Java.
  3. Kotlin على Android تستفيد من JVM ecosystem، لكنها تنتهي إلى DEX يعمل على ART.
  4. Kotlin وJava تستطيعان التعايش داخل التطبيق نفسه، ولذلك لا تحتاج إلى إعادة كتابة مشروع قائم للاستفادة من Kotlin.
  5. K2 يطوّر compilation وcode analysis، بينما تظل بيئة تشغيل تطبيق Android منفصلة عن compiler.

النتيجة التي يجب أن تكون قادرًا على الوصول إليها: عندما ترى Kotlin code داخل مشروع Android، ينبغي أن تستطيع تحديد ما الذي تضمنه اللغة، وما الذي يضمنه compiler، وما الذي يعتمد على Android runtime، وما الذي لا يمكن ضمانه إلا من خلال تصميم التطبيق واختباره.
